This page explains how to obtain the lab template from GitHub and describes the structure and use of each directory. Please read through this page before starting the labs.

## Getting the Lab Template

The labs in this course are based on Loongson's official teaching lab environment `cdp_ede_local`, modified so that it runs correctly on the DIGILENT NEXYS 100T development board. The modified repository is at: [cdp_ede_local](https://github.com/zihaojf/cdp_ede_local)

Clone it locally first. **We recommend putting it under Windows**, not inside WSL2.

```bash
git clone git@github.com:zihaojf/cdp_ede_local.git
```

!!! tip

    We recommend that you manage your own versions carefully during development!

Once cloned, the repository root is structured as follows:

```text
cdp_ede_local/
├── README.md          # Documentation: lab schedule and corresponding environments
├── dc_env/            # Labs 1-4: fundamentals of digital logic circuits
├── minicpu_env/       # Lab 5: single-cycle CPU with 5 instructions
└── mycpu_env/         # Labs 6-23: everything from the 20-instruction CPU onward
```

The three environments **correspond to the three phases of the course labs**. They are independent of one another and are used in sequence as the labs progress.

## dc_env (Labs 1–4)

```text
dc_env/
├── exp1/    Running light
├── exp2/    Register file simulation
├── exp3/    Synchronous/asynchronous RAM
└── exp4/    Digital logic circuit design and debugging
```

Each `expN` directory comes with a source file skeleton, a testbench, and constraints (`.xdc`). Either open it directly in Vivado, or create a new project and add the source files. **Your job is to complete/fix the source files, get the simulation passing, then run synthesis and program the board.**

## minicpu_env (Lab 5)

```text
minicpu_env/
├── func/           # Test programs: assembly → instruction memory initialization file
│   ├── start.S         # Fibonacci program (runs with only 5 instructions)
│   ├── Makefile        # Cross-compilation; produces inst_ram.coe / inst_ram.txt
│   └── inst_ram.coe    # Compiled instruction image (for simulation)
├── miniCPU/        # CPU RTL
│   ├── minicpu_top.v   # Single-cycle CPU top level
│   ├── regfile.v       # Register file
│   └── tools.v         # Helper components
└── soc_verify/     # SoC verification environment
    ├── rtl/            # soc_mini_top.v + CONFREG + xilinx_ip
    └── testbench/      # mycpu_tb.v: simulation top level
```

A minicpu capable of running five instructions is already provided. Run the simulation in the Vivado project under `soc_verify`: the CPU fetches instructions from `inst_ram` and executes the Fibonacci program in `func`, and the result is verified through the CONFREG (observed during simulation) or the seven-segment display (on the board).

## mycpu_env (Labs 6–23)

This is the environment you will use for most of the course; all subsequent labs are developed **incrementally** on top of it.

```text
mycpu_env/
├── myCPU/              # Your CPU RTL
│   ├── mycpu_top.v     # CPU top level
│   ├── alu.v, regfile.v, decoder_*.v ...
├── func/               # The func functional test program suite
│   └── inst/           # n1-n79 per-feature test assembly (each file targets a few instructions)
├── gettrace/           # Reference trace generator (for trace-comparison debugging)
├── module_verify/      # Standalone module verification (Lab 17 TLB, Lab 20 Cache)
│   ├── tlb_verify/     # Lab 17: TLB module verification
│   ├── cache_verify/   # Lab 20: Cache module verification
│   ├── mul_verify/     # Multiplier verification
│   ├── div_verify/     # Divider verification
└── soc_verify/         # SoC verification environment, split into four directories by bus interface
    ├── soc_dram/       # Lab 6: distributed RAM interface (single-cycle)
    ├── soc_bram/       # Labs 7-13: block RAM interface (pipeline/exceptions)
    ├── soc_hs_bram/    # Lab 14: BRAM interface with handshake
    └── soc_axi/        # Labs 15-23: AXI bus interface
```

!!! warning "Two things to note"

    1. The initial code in `myCPU/` **contains functional bugs**. This is part of the lab design (find them and fix them), not a repository bug;
    2. Each lab corresponds to a **different SoC directory** under `soc_verify` — pay attention to which directory the simulation or board project uses.


!!! note "Toolchain"

    The Makefile in `func/` depends on the `loongarch32r-linux-gnusf-*` cross-compilation toolchain (needed when you compile the test programs yourself). For simulation and verification you usually only need the `inst_ram.coe` image shipped with the repository — just run it directly.

## Lab Environment Checklist

Before starting Lab 2, confirm each of the following:

- [ ] Vivado ≥ 2019.2 is installed, and you can create a project and get a simulation running;
- [ ] WSL2/Ubuntu is available, with the basic tools `gcc`, `make`, and `git` in place;
- [ ] The LoongArch32 cross-compilation toolchain is installed and added to `PATH`;
- [ ] You have set up your own code repository

Now let's start the labs!
