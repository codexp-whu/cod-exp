# Lab 16: Completing AXI Random-Delay Verification

!!! info "Reference in the Book"

    [*CPU Design in Practice: LoongArch Edition*, 8.1.3 Practical Task 16: Completing AXI Random-Delay Verification](https://bookdown.org/loongson/_book3/chapter-axi-bus.html#subsec-exp16)

## Objectives

- Refine the AXI bus interface design and verify the CPU's functionality and the robustness of its handshake under random bus delays.

## Tasks

In this practical task you build on the CPU you completed in Lab 15 and do the following:

Refine the AXI bus interface design so that it completes the **random-delay functional verification of the func program for exp16** in the AXI-based SoC verification environment; it must pass both simulation and board verification.

!!! warning "Why random delays expose bugs"

    A fixed-delay response masks handshake timing problems: bugs such as `READY` arriving late, `VALID` being de-asserted at the wrong moment, or data being lost during a multi-cycle wait only come to light once the delay is randomized. The random delay is generated by the pseudo-random number generator in `confreg.v`, and in simulation its initial seed is controlled by the `RANDOM_SEED` macro.

## Steps

1. Update the code of your CPU implementation into the `mycpu_env/myCPU/` directory.
2. Edit the func configuration file, `mycpu_env/func/include/test_config.h`: select the exp16 configuration and compile. (`make EXP=16`)
3. Open the `gettrace` project, `mycpu_env/gettrace/gettrace.xpr`. Run the simulation of the `gettrace` project (once the simulation window opens, just click run all and wait for it to finish) to generate a new reference trace file, `golden_trace.txt` (`mycpu_env/gettrace/golden_trace.txt`). The simulation has to run to completion before `golden_trace.txt` holds its full contents.
4. Go to the `mycpu_env/soc_verify/soc_axi/run_vivado/` directory and launch the project that verifies myCPU. If no project has been created in that directory yet, use the `create_project.tcl` file there to create one.
5. Re-customize `axi_ram` in the project.
6. **Change the `RANDOM_SEED` macro in `mycpu_env/soc_verify/soc_axi/rtl/CONFREG/confreg.v` to a different value**, then run the simulation in the myCPU verification project (once the simulation window opens, just click run all) and verify and debug the design until the simulation passes.
7. Repeat the previous step several times; the values you set for the `RANDOM_SEED` macro must cover all **three random delay types** (long delay, short delay and no delay).
8. Run synthesis and implementation in the myCPU verification project, generate the bitstream file, and verify on the board.

## Acceptance Criteria

- [ ] The Lab 16 test program (n1~n58, 58 feature points in total) passes in simulation, and several sets of `RANDOM_SEED` covering the three delay types all pass.
- [ ] On the board both bicolor LEDs are green, and the seven-segment display shows "3A00 003A".

??? tips "Board verification requirements"

    On the board, func must run correctly every time you **"toggle the DIP switches at random and then press reset"** (the DIP switch state during reset serves as the initial random seed). If you see the "passes in simulation but fails on the board" phenomenon, debug it as described in Lab 14: write the failing seed into `RANDOM_SEED` in `confreg.v` and reproduce the failure in simulation; if it cannot be reproduced, look for coding-standard problems in your code, or use the Vivado logic analyzer for in-circuit debugging.
