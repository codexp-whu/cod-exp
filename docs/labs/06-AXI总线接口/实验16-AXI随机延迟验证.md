# 实验16：完成AXI随机延迟验证

!!! info "原书参考"

    [《CPU设计实战：LoongArch版》8.1.3 实践任务16：完成AXI随机延迟验证](https://bookdown.org/loongson/_book3/chapter-axi-bus.html)

## 实验目标

- 在总线应答**随机延迟**的压力下验证 CPU 功能正确。
- 排查并消灭两类典型 bug：**握手违例**与**死锁/活锁**。
- 建立可复用的随机验证环境（可回归、可播种复现）。

## 知识背景

### 为什么需要随机延迟

固定当拍应答的总线，掩盖了一切时序 bug：

- 等待逻辑中"多等一拍就丢数据"的错误，恒速应答永远撞不上；
- 握手状态机里"valid 撤销时机"的错误，只有 `ready` 迟到才暴露。

随机延迟把总线时序的不确定性推向极限：每次事务的应答延迟在 0~N 拍间随机取值。功能仍正确的 CPU，才算真正"会等"。

### 典型 bug 模式

1. **握手违例**：`ready` 采样时刻错误，导致同一请求被应答两次，或请求被跳过——数据错乱；
2. **死锁**：CPU 等 `ready`，从端等 `valid`，双方互等——仿真挂死；
3. **超时丢失**：应答延迟很长时，CPU 状态机因计数器溢出提前放行。

### 验证方法学

- 随机延迟用**伪随机数 + 种子**驱动：失败的用例可用种子精确复现；
- 每轮回归换不同种子跑多组，观察是否稳定全过；
- 死锁检测：仿真加看门狗，超时自动终止并报告现场。

## 任务要求

1. 为 AXI 从端（或转换桥）加随机延迟逻辑：读/写各通道独立随机延迟 0~N 拍（N 建议 ≥16）；
2. 在随机延迟下全量回归功能测试，多组种子；
3. 记录并修复暴露出的全部 bug（如无 bug，调大 N、增加种子数继续轰炸）；
4. 每个修复的 bug 记录：触发场景、根因、修复方式。

## 验收标准

- [ ] 多组种子下功能测试全部通过；
- [ ] 连续长时间仿真无死锁（看门狗不触发）；
- [ ] 实验报告含随机验证环境说明与 bug 记录（数量不限，重在真实）。
