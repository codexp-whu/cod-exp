    进阶写法¶

    这一节不是基础五级流水线的前置内容。第一次阅读时可先了解 Decoupled，其余部分可在 CPU 基本功能完成后查阅。

    Decoupled 握手¶

    在流水线 CPU 中，相邻两级之间不是每时每刻都能传递数据的。

    Load-use 冒险需要 stall，跳转需要 flush；Cache 和总线还可能有不确定延迟。Chisel 标准库用 DecoupledIO 统一表达 ready/valid 握手，但协议不会自动替你处理分支冲刷或流水线状态。

    在前面的流水线例子中，stall 和 flush 由各级寄存器的条件连接控制。连接 I-Cache、数据总线等具有等待周期的模块时，还需要统一表示“请求是否有效”和“对端能否接收”。DecoupledIO 提供了这组握手信号。

    DecoupledIO 的三个组成部分¶

    // DecoupledIO 的简化定义（在 chisel3.util 中）
class DecoupledIO[T <: Data](gen: T) extends Bundle {
    val ready = Input(Bool())    // 接收方说"我可以收了"
    val valid = Output(Bool())   // 发送方说"我有数据要传"
    val bits  = Output(gen)      // 实际数据（类型为泛型 T）
}

    一次成功传输发生在 ready && valid 同时为真的时钟沿，也就是常说的 fire。

    生产者拉高 valid 后，在传输完成前应保持 valid 和 bits 不变。否则接收方施加反压时，等待中的数据可能发生变化。

    Decoupled 只定义接口协议

    DecoupledIO 提供 ready、valid、bits 和相关辅助方法。生产者是否正确保持数据、队列是否足够深、错误路径上的请求如何取消，仍然需要设计者处理。

    基本用法¶

    // 生产者：声明 Decoupled 输出端口
class Producer extends Module {
    val io = IO(new Bundle {
        val out = Decoupled(UInt(32.W))
    })
    val dataReg = RegInit(0.U(32.W))

    io.out.bits  := dataReg
    io.out.valid := true.B

    when(io.out.fire) { dataReg := dataReg + 1.U }
}

    // 消费者：声明 Decoupled 输入端口
class Consumer extends Module {
    val io = IO(new Bundle {
        val in     = Flipped(Decoupled(UInt(32.W)))
        val enable = Input(Bool())
    })
    val dataReg = RegInit(0.U(32.W))
    io.in.ready := io.enable

    when(io.in.fire) {
        dataReg := io.in.bits
    }
}

    Flipped 的作用：Decoupled 的默认方向是"输出"（ready 输入 + valid/bits 输出）。

    而消费者需要反过来：ready 输出 + valid/bits 输入。Flipped 一键完成这个方向翻转，不需要手动重写三个字段的 Input/Output。

    fire()¶

    DecoupledIO 提供了几个便捷方法，其中fire表示ready和valid信号同时拉高，即发送成功：

    io.out.ready
io.out.valid
io.out.bits
io.out.fire   // 等价于 io.out.ready && io.out.valid

    生产者发送侧常见的写法：

    // 典型的 Decoupled 生产者：fire 后更新下一笔数据
when(io.out.fire) {
    // 上一笔数据已被接收，准备下一笔
    dataReg := nextData
}

    有限长度的数据源可以再增加一个 validReg；最后一笔发送完成后将它拉低。

    批量连接 <>¶

    Chisel 提供了 <> 运算符来批量连接两个结构相同的 Bundle：

    producer.io.out <> consumer.io.in
// 等价于：
// consumer.io.in.ready -> producer.io.out.ready
// producer.io.out.valid -> consumer.io.in.valid
// producer.io.out.bits  -> consumer.io.in.bits

    <> 匹配同名字段，并根据 Input/Output 方向建立连接。结构和方向兼容的接口可以整体连接，不必逐字段写 :=。

    Queue¶

    Queue 在生产者和消费者之间插入 FIFO，并传播反压：

    val producer = Module(new Producer)
val consumer = Module(new Consumer)

consumer.io.in <> Queue(producer.io.out, 2)

    需要其他行为时，改用带参数的版本，而不是同时保留上面的连接：

    consumer.io.in <> Queue(
    producer.io.out,
    entries = 4,        // FIFO 深度
    pipe    = true,
    flow    = false
)

    基本行为如下：

    • 消费者 ready=0 时，数据暂存在队列中
    • 队列满时，生产者看到 ready=0 从而自动暂停
    • 队列空时，消费者看到 valid=0 从而知道没有数据可用

    flow = true 允许队列为空时从输入组合直通输出；pipe = true 允许队列已满但同拍出队时继续入队。二者都会改变 ready/valid 的组合路径，不应简单理解成“额外打一拍”。是否改善时序要看具体连接和综合结果。

    Pipe¶

    Pipe 处理的是 ValidIO，只延迟 valid 和 bits，没有 ready，也没有反压：

    val staged1 = Pipe(io.in)
val staged3 = Pipe(io.in, latency = 3)

    它适合“消费者每拍都能接收”的延迟通路。如果下游可能暂停，应使用 DecoupledIO 配合 Queue，不能用 Pipe 代替。

    Bundle 与 Decoupled 的选择

    场景 写法 原因
    流水线级间（有 stall/flush，控制逻辑需要精确到每一拍） 普通 Bundle + when 手动控制 分别描述保持、清空和正常更新
    取指 ↔ I-Cache、访存 ↔ 总线 DecoupledIO 请求可能等待，需要 ready/valid 握手
    两个速率不匹配的模块之间 DecoupledIO + Queue Queue 暂存尚未被下游接收的数据
    单方向推送，不需反压（如中断信号、分支预测结果） ValidIO（见下一节） 接口中不包含 ready

    基础五级流水线的级间寄存器建议使用 Bundle 并手动处理 stall/flush。连接 Cache、总线等可能等待的模块时，再考虑 Decoupled。

    其他常用构建原语¶

    除 Mux、RegInit 和 Bundle 外，chisel3.util 还提供 ValidIO、Counter、ShiftRegister 和 Arbiter 等常用组件。下面说明它们的接口和适用条件。

    ValidIO¶

    ValidIO 只有 valid 和 bits，没有 ready。它适用于消费者始终能够接收数据、不需要反压的单向通路。

    // ValidIO 的定义（在 chisel3.util 中）
class ValidIO[T <: Data](gen: T) extends Bundle {
    val valid = Output(Bool())
    val bits  = Output(gen)
}

    // 生产者：声明 Valid 输出
class BranchPredictor extends Module {
    val io = IO(new Bundle {
        val prediction = Valid(UInt(32.W))   // 预测的目标地址 + 是否有效
    })
    io.prediction.bits  := predictedTarget
    io.prediction.valid := hasPrediction     // 没有预测时 valid=0，bits 值无效
}

// 消费者：取指单元检查 valid 决定是否跳转
val pc_next = Mux(predictor.io.prediction.valid,
                  predictor.io.prediction.bits,
                  pc + 4.U)
    场景 用什么 理由
    消费者可能无法接收，需要反压 DecoupledIO 消费者可通过 ready 暂缓传输
    消费者总是能接收，只传递数据和有效标志 ValidIO 接口中不包含 ready

    Counter¶

    Counter 实现了计数器的功能，封装了"条件计数 + 到达上限时回绕"的常见模式：

    // Counter(cond, n)：cond 为 true 时计数 +1，计到 n-1 后下一个周期回 0
val (count, wrap) = Counter(true.B, 32)        // 每周期 +1，0→31→0→31→...
val (count, wrap) = Counter(en, 100)           // 有条件计数

// count: UInt —— 当前计数值（0 到 n-1）
// wrap:  Bool —— 当 count === n-1 且 cond 为 true 时为真

    多周期除法器的迭代计数：

    val (cycle, done) = Counter(state === RUN, 32)  // RUN 状态每周期 +1

when(state === RUN) {
    // 迭代除法算法的每一步
    remainder := remainder - divisor
    // ...
    when(done) { state := DONE }   // 32 个周期后完成
}

    对比手写版本：

    // 手写版本容易忘记 wrap 条件判断的细节
val cycle = RegInit(0.U(5.W))
when(state === RUN) {
    cycle := cycle + 1.U
}
val done = cycle === 31.U && state === RUN

// Counter 版本意图更清晰，且自动处理位宽
val (cycle, done) = Counter(state === RUN, 32)

    Counter 自动推断位宽

    Counter(cond, n) 中的 n 是 Scala Int，count 的位宽取 log2Ceil(n)，能够表示 0 到 n-1。

    ShiftRegister¶

    ShiftRegister 可以实现打多拍，等价于多个 RegNext 串联，加上可选的使能信号：

    // ShiftRegister(in, n)：将 in 延迟 n 拍
val delayed = ShiftRegister(io.in, 3)
// 等价于：
// val delayed = RegNext(RegNext(RegNext(io.in)))

// ShiftRegister(in, n, en)：带使能的版本——en=1 时移位，en=0 时保持
val delayed = ShiftRegister(io.in, 3, en)
// 等价于 3 个带使能的 RegEnable 串联

// ShiftRegister(in, n, resetData, en)：额外指定复位值
val delayed = ShiftRegister(io.in, 3, 0.U, en)

    CPU 中的典型场景——将控制信号和延迟后的数据对齐：

    // EX 阶段计算出的 aluResult 经过 MEM→WB 两级才写回
// regWrite 标志也需要打同样的拍数，保持与数据同步
val regWrite_mem = RegNext(regWrite_ex)
val regWrite_wb  = RegNext(regWrite_mem)

// 用 ShiftRegister 一行搞定
val regWrite_delayed = ShiftRegister(regWrite_ex, 2)   // 打 2 拍，对齐到 WB

    Arbiter多选一调度器¶

    当多个请求源竞争同一个资源时（如两个 Master 共享总线），仲裁器在它们之间做仲裁。chisel3.util 提供了两种现成的仲裁器：

    val arb = Module(new Arbiter(UInt(32.W), 4))
arb.io.in(0) <> req0
arb.io.in(1) <> req1
arb.io.in(2) <> req2
arb.io.in(3) <> req3
arb.io.out <> sharedBus

    轮询仲裁器的接口相同：

    val rrArb = Module(new RRArbiter(UInt(32.W), 4))

    区分 Arbiter 与 RRArbiter

    Arbiter 是固定优先级仲裁器，多个输入同时有效时选择编号较小者；RRArbiter 使用轮询策略。

    两者的输入输出都是 DecoupledIO。被选中的请求者 valid=1 且输出端 ready=1 时，一笔传输完成；轮询仲裁器随后更新优先起点，固定优先级仲裁器仍从编号较小的有效请求开始选择。

    CPU 中的仲裁示例

    单核教学 CPU 中不一定会用到 Arbiter。I-Cache 和 D-Cache 需要共享一个外部总线接口时，可以使用仲裁器选择当前请求。

    PriorityMux 与 PriorityEncoder¶

    PriorityEncoder 找出置位比特中优先级最高者的编号；默认是低位优先。PriorityMux 则按列表顺序选择第一个满足条件的值。

    val irq = Wire(UInt(8.W))

// irq(0) 优先级最高，其次是 irq(1)
val irqNum = PriorityEncoder(irq)

    当 irq 全为零时，编码结果也是零，因此还要单独检查 irq.orR 才能判断是否真的有请求。

    // PriorityMux: 按优先级选择——第一个满足条件的值被选中
val result = PriorityMux(Seq(
    (cond0) -> value0,    // 优先级最高——cond0 先被检查
    (cond1) -> value1,
    (cond2) -> value2     // 优先级最低
))

    PriorityMux、MuxCase 与 Mux1H

    PriorityMux 和 MuxCase 都表达有顺序的优先级选择，不要求条件互斥。只有 Mux1H 假定选择条件是 one-hot；多项同时为真时，它会把候选数据按位或起来。

    参数化与代码生成¶

    Scala 的构造参数、集合和函数可以用来生成可配置的硬件结构。下面看三种课程项目中常用的模式。

    泛型 Module¶

    把位宽、深度、数量等参数写在 class 的构造函数中，实例化时传入不同参数就能生成不同规格的模块：

    // 参数化 ALU：位宽可变
class Alu(width: Int) extends Module {
    val io = IO(new Bundle {
        val a   = Input(UInt(width.W))
        val b   = Input(UInt(width.W))
        val op  = Input(UInt(4.W))
        val out = Output(UInt(width.W))
    })
    io.out := MuxLookup(io.op, 0.U(width.W))(Seq(
        AluOp.ADD -> (io.a + io.b),
        AluOp.SUB -> (io.a - io.b),
        // ...
    ))
}

// 实例化 32 位和 64 位两种 ALU
val alu32 = Module(new Alu(32))
val alu64 = Module(new Alu(64))
// 两个实例使用相同结构，位宽参数不同

    // 参数化寄存器堆：寄存器数量和位宽都可配置
class RegFile(regCount: Int, xlen: Int) extends Module {
    val addrWidth = log2Ceil(regCount)
    val io = IO(new Bundle {
        val rs1 = Input(UInt(addrWidth.W))     // 地址位宽自动匹配寄存器数量
        val rs2 = Input(UInt(addrWidth.W))
        val rd  = Input(UInt(addrWidth.W))
        val wen = Input(Bool())
        val wdata = Input(UInt(xlen.W))
        val rdata1 = Output(UInt(xlen.W))
        val rdata2 = Output(UInt(xlen.W))
    })
    val rf = RegInit(VecInit(Seq.fill(regCount)(0.U(xlen.W))))
    io.rdata1 := Mux(io.rs1 === 0.U, 0.U, rf(io.rs1))
    io.rdata2 := Mux(io.rs2 === 0.U, 0.U, rf(io.rs2))
    when(io.wen && io.rd =/= 0.U) {
        rf(io.rd) := io.wdata
    }
}

    RV32 和 RV64 都有 32 个通用整数寄存器，区别在数据位宽：

    val rf32 = Module(new RegFile(32, 32))
val rf64 = Module(new RegFile(32, 64))

    Scala 代码运行在生成阶段

    构造函数参数、log2Ceil 和 Seq.fill 都属于 Scala。if、for 和函数可以在生成阶段决定模块数量、位宽与连接结构，但不会成为硬件运行时的控制流程。

    用 BitPat 编写译码表¶

    指令译码中的“不关心位”应使用 BitPat 的 ?，而不是硬件值 DontCare。下面假定 InstType 和 AluOp 使用 UInt 编码，ListLookup 可以一次查出多项控制信号：

    val default = List(InstType.ILLEGAL, AluOp.NOP, 0.U(1.W))

val table = Array(
  BitPat("b0000000??????????000?????0110011") ->
    List(InstType.ADD, AluOp.ADD, 1.U(1.W)),
  BitPat("b0100000??????????000?????0110011") ->
    List(InstType.SUB, AluOp.SUB, 1.U(1.W))
)

    执行查表后再给各项结果命名：

    val decoded = ListLookup(io.inst, default, table)

val instType = decoded(0)
val aluOp    = decoded(1)
val regWrite = decoded(2).asBool

    这种表格把指令位模式和控制信号放在一起。新增指令时仍要补测试，尤其要检查两条 BitPat 是否可能同时匹配。

    for / yield¶

    当模块的端口数量或子模块数量由参数决定时，for / yield 是标配工具：

    val banks = Seq.fill(numBanks)(Module(new CacheBank(bankSize)))

banks.zipWithIndex.foreach { case (bank, i) =>
  bank.io.addr  := io.addr
  bank.io.wdata := io.wdata
  bank.io.wen   := io.wen && (bankSel === i.U)
}

    各 Bank 的命中信号若保证 one-hot，可以直接选择读数据：

    val choices = banks.map(bank => bank.io.hit -> bank.io.rdata)
io.rdata := Mux1H(choices)

    // 流水线延迟线：N 级参数化
class DelayLine[T <: Data](gen: T, stages: Int) extends Module {
    val io = IO(new Bundle {
        val in  = Input(gen)
        val out = Output(gen)
    })
    io.out := (0 until stages).foldLeft(io.in) { (sig, _) =>
        RegNext(sig)   // 每一级打一拍，共 stages 拍
    }
}

// 使用：生成一个 5 级延迟线
val delay = Module(new DelayLine(UInt(32.W), 5))

    用 foldLeft 生成级联结构

    foldLeft 是 Scala 集合上的高阶函数，它将一个初始值和集合中的每个元素依次结合：

    // foldLeft 展开过程（以 stages=3 为例）
(0 until 3).foldLeft(io.in) { (sig, _) => RegNext(sig) }
// = RegNext(RegNext(RegNext(io.in)))

    foldLeft 很适合生成一级接一级的重复结构，例如延迟线或旁路选择链。它按顺序折叠，不会自动把运算改造成平衡树。

    Counter、Queue 和参数化模块可在相应场景中选用。基础 CPU 的时序与行为确认后，再用这些组件整理重复结构。
