    仿真与测试¶

    生成 SystemVerilog 说明代码通过了生成阶段，但电路功能仍需测试。流水线 CPU 中常见的问题是时序问题。

    这节先从一个加法器开始，最后再把方法用到整颗 CPU 上。

    测试时有哪些工具¶

    课程模板使用 ChiselTest 编写测试，测试流程涉及以下工具：

    工具 负责什么
    ScalaTest 组织测试用例，报告通过或失败
    ChiselTest 提供 poke、peek、expect、step 等操作
    仿真后端 执行生成出来的 RTL
    Mill 编译源码并启动测试

    测试代码放在 mycpu/test/src/。运行全部测试：

    ./mill mycpu.test

    只运行某个测试类时，可以使用：

    ./mill mycpu.test.testOnly AdderSpec

    项目稳定后，也可以让 Mill 在保存文件时自动重跑：

    ./mill -w mycpu.test

    先认识四个动作¶

    假设 dut 是正在测试的模块：

    写法 含义 类比 Verilog testbench
    poke 给输入端口设置当前值 给输入信号赋值
    peek 读取当前信号值 $display 或查看波形
    expect 读取并检查是否等于期望值 不相等就 $error
    clock.step(n) 推进 n 个时钟周期 产生 n 个完整时钟周期

    dut 是 Device Under Test 的缩写，中文就是“被测模块”。这只是测试代码中的变量名，不是 Chisel 关键字。

    常用的几行测试代码如下：

    dut.io.a.poke(3.U)
dut.io.b.poke(4.U)
dut.io.sum.expect(7.U)

val observed = dut.io.sum.peek().litValue
println(s"sum = $observed")

    能直接判断对错时优先用 expect。peek 更适合临时观察，或者把输出读回 Scala 后参与更复杂的判断。

    第一个组合逻辑测试¶

    继续测试环境章节中的 Adder。新建 mycpu/test/src/AdderSpec.scala：

    import chisel3._
import chiseltest._
import org.scalatest.flatspec.AnyFlatSpec

class AdderSpec extends AnyFlatSpec
    with ChiselScalatestTester {
  "Adder" should "add two 8-bit numbers" in {
    test(new Adder) { dut =>
      dut.io.a.poke(3.U)
      dut.io.b.poke(4.U)
      dut.io.sum.expect(7.U)
    }
  }
}

    这里没有 clock.step()。加法器是组合逻辑，输入改变后，仿真器会重新计算组合网络，随后就能检查输出。

    可以把期望值暂时改成 8.U，观察失败信息中是否包含实际值、期望值和对应的测试位置。

    测试类的基本结构

    AnyFlatSpec、should 和 in 属于 ScalaTest。现阶段不需要系统学习 ScalaTest，只要知道每个 in 对应一个相对独立的测试场景即可。

    时序逻辑要明确检查周期¶

    下面是一个带使能的计数器：

    class Counter extends Module {
  val io = IO(new Bundle {
    val enable = Input(Bool())
    val count = Output(UInt(8.W))
  })

  val count = RegInit(0.U(8.W))
  when(io.enable) { count := count + 1.U }
  io.count := count
}

    测试开始时先显式复位：

    dut.reset.poke(true.B)
dut.clock.step(2)
dut.reset.poke(false.B)

    不要依赖仿真器“好像替我复位过”。显式复位能让测试的起点固定，也方便以后切换仿真后端。

    完整测试中的关键部分如下：

    test(new Counter) { dut =>
  dut.reset.poke(true.B)
  dut.clock.step(2)
  dut.reset.poke(false.B)

  dut.io.enable.poke(true.B)
  dut.io.count.expect(0.U)
  dut.clock.step()
  dut.io.count.expect(1.U)

  dut.io.enable.poke(false.B)
  dut.clock.step()
  dut.io.count.expect(1.U)
}

    请留意第一次 expect(0.U) 的位置：enable 虽然已经拉高，但时钟沿还没来，寄存器仍是旧值。step() 之后，计数器才变成 1。

    测试时序模块时，可以固定按这个节奏写：

    1. 设置本拍输入。
    2. 如有必要，检查时钟沿前的输出。
    3. step() 推进一拍。
    4. 检查寄存器更新后的输出。

    暂停、冲刷和转发测试也按这个顺序逐拍设置输入并检查状态。

    用表格列测试用例¶

    当输入组合变多时，不要复制几十段 poke。先把“输入和正确答案”写成 Scala 数据，再用循环执行。

    以一个简化 ALU 为例：

    val cases = Seq(
  (0, 10, 3, 13),
  (1, 10, 3, 7),
  (2, 10, 3, 2),
  (3, 10, 3, 11)
)

    逐项喂给被测模块：

    for ((op, a, b, expected) <- cases) {
  dut.io.op.poke(op.U)
  dut.io.a.poke(a.U)
  dut.io.b.poke(b.U)
  dut.io.out.expect(expected.U)
}

    这种写法共用一份检查逻辑。增加测试时在表中添加数据即可，也能减少复制代码时漏改期望值的问题。

    参考模型：用 Scala 算正确答案¶

    ALU、立即数生成器和地址计算器适合使用参考模型。参考模型用普通 Scala 计算期望结果，不再写一份 Chisel 电路。

    def aluRef(op: Int, a: BigInt, b: BigInt): BigInt = {
  op match {
    case 0 => a + b
    case 1 => a - b
    case 2 => a & b
    case 3 => a | b
  }
}

    如果硬件输出固定为 32 位，参考模型也要模拟 32 位截断：

    val mask = (BigInt(1) << 32) - 1
val expected = aluRef(op, a, b) & mask
dut.io.out.expect(expected.U)

    这一步很重要。Scala 的 BigInt 不会像 32 位硬件那样自然溢出；如果参考模型不做掩码，可能是测试答案错了，而不是电路错了。

    先测边界，再加随机测试¶

    随机测试用于补充覆盖，边界情况仍应单独列出。以 8 位加法器为例，可以覆盖：

    • 0 + 0 和 0 + 最大值；
    • 1 + 最大值，检查回绕；
    • 最高位从 0 变 1 的情况；
    • 两个最大值相加。

    可以先写一组有意挑选的边界值：

    val edges = Seq(0, 1, 127, 128, 254, 255)

for (a <- edges; b <- edges) {
  dut.io.a.poke(a.U)
  dut.io.b.poke(b.U)
  dut.io.sum.expect(((a + b) & 0xff).U)
}

    边界用例通过后，再补随机输入。随机数种子要固定：

    val random = new scala.util.Random(20250828L)

for (_ <- 0 until 500) {
  val a = random.nextInt(256)
  val b = random.nextInt(256)
  dut.io.a.poke(a.U)
  dut.io.b.poke(b.U)
  dut.io.sum.expect(((a + b) & 0xff).U)
}

    固定种子可以让失败时的随机输入保持一致，便于重复运行和定位。未固定种子时，每次测试使用的数据不同，错误可能难以复现。

    波形用来回答“为什么错”¶

    expect 适合回答“哪里第一次不对”，波形适合回答“它为什么会不对”。给测试增加 WriteVcdAnnotation 就能生成 VCD：

    import chiseltest.simulator.WriteVcdAnnotation

test(new Counter)
    .withAnnotations(Seq(WriteVcdAnnotation)) { dut =>
  dut.io.enable.poke(true.B)
  dut.clock.step(10)
}

    测试日志会给出运行目录。找不到文件时，可以在项目根目录搜索：

    find . -name '*.vcd'

    用 GTKWave 打开：

    gtkwave 找到的波形文件.vcd

    不要默认给所有回归测试开 VCD。流水线 CPU 信号多、周期长，波形文件很快会变大，写文件本身也会拖慢仿真。更实用的做法是先不开波形跑回归，定位到失败用例后，只给这一个测试打开 VCD。

    Verilator 是什么¶

    Verilator 是 RTL 仿真器。它会把 Chisel 生成的 SystemVerilog 转换成 C++ 仿真模型，再调用 g++ 和 make 编译成本地可执行程序。ChiselTest 随后通过这个程序驱动时钟、设置输入并读取输出。

    Verilator 不负责综合，也不会生成 FPGA 配置文件。它与 Vivado 在本课程中的分工如下：

    • Verilator 用来检查 RTL 在仿真中是否按预期工作。
    • Vivado 用来综合、实现并生成上板文件。

    Verilator 每次启动一个新设计时，需要先生成并编译 C++ 模型，所以很短的小测试可能感觉启动偏慢。模型编译完成后，长时间运行通常较快，因此更适合整颗 CPU、长程序和批量回归。

    安装和检查¶

    在 Ubuntu、WSL2 或 Linux 虚拟机中安装：

    sudo apt update
sudo apt install -y verilator build-essential

    检查版本：

    verilator --version
g++ --version
make --version

    课程模板若规定了最低 Verilator 版本，以模板为准。Ubuntu 软件源中的版本过旧时，不要自行混装多个版本，先按课程说明升级发行版或使用统一的工具安装方案。

    在 ChiselTest 中选择 Verilator¶

    显式添加后端注解：

    import chiseltest.simulator.VerilatorBackendAnnotation

test(new MyCPU)
    .withAnnotations(Seq(VerilatorBackendAnnotation)) { dut =>
  dut.clock.step(20)
}

    需要同时看波形时，可以加入两个注解：

    val annotations = Seq(
  VerilatorBackendAnnotation,
  WriteVcdAnnotation
)

test(new MyCPU).withAnnotations(annotations) { dut =>
  dut.clock.step(20)
}

    VCD 会明显增加磁盘写入量。对长程序，先只开 Verilator；确定出错周期后，再缩短程序或周期数并打开 VCD。

    常见 Verilator 报错¶

    现象 先检查什么
    verilator: command not found 是否安装 Verilator，终端是否在 Linux 环境
    找不到 g++ 或 make 是否安装 build-essential
    提示不支持某段 SystemVerilog Verilator 是否过旧，生成的 RTL 是否用了不受支持的结构
    C++ 编译占满内存 是否同时启动了过多测试，虚拟机内存是否太小
    构建目录权限错误 项目是否放在只读目录，是否曾用 sudo 运行 Mill

    不要使用 sudo ./mill ...。一旦 Mill 输出目录被 root 用户创建，之后普通用户就可能无法覆盖。课程项目应放在自己的 Linux 主目录中，以普通用户运行。

    整颗 CPU 应该怎么测¶

    CPU 测试建议按模块、部件、冒险场景和程序逐级进行：

    层次 例子 主要检查
    单元测试 ALU、译码器、立即数生成器 单拍输入输出是否正确
    部件测试 寄存器堆、PC、流水线寄存器 复位、写使能、保持是否正确
    冒险测试 转发、load-use、跳转冲刷 指令是否停在正确级，气泡是否插对
    程序测试 一小段手写汇编 最终寄存器和内存状态
    回归测试 指令测试集 修改后是否破坏已有功能

    每增加一种指令或控制功能，就补一个最小测试。例如实现转发时，至少分别覆盖：

    • EX 到 EX 的数据相关；
    • MEM 到 EX 的数据相关；
    • 两个来源同时匹配时的优先级；
    • 目的寄存器为 x0 时不得错误转发。

    实现暂停和冲刷时，除最终结果外，还应观察各级 valid、PC 和写使能，确认错误路径上的指令没有产生寄存器写入或存储器写入。

    给程序测试加周期上限¶

    CPU 未能执行到结束条件时，测试中的 while 会持续运行。每个程序测试都应设置最大周期数：

    val maxCycles = 2000
var cycles = 0

while (!dut.io.halt.peek().litToBoolean &&
       cycles < maxCycles) {
  dut.clock.step()
  cycles += 1
}

assert(dut.io.halt.peek().litToBoolean,
  s"CPU did not finish in $maxCycles cycles")

    halt、调试寄存器端口和程序加载方式要按课程 CPU 顶层接口调整。测试中需要同时定义结束条件和最大等待周期。

    程序结束后，再检查约定的可观察状态：

    dut.io.debugRegs(10).expect(42.U)
dut.io.debugMem(0).expect("h12345678".U)

    检测到 halt 后，还应检查约定的寄存器和内存结果。CPU 也可能沿错误路径执行到结束指令。

    出错时按什么顺序查¶

    一颗流水线 CPU 出错后，建议按下面的顺序收缩范围：

    1. 找到第一个失败的测试，并查看最早出现的报错。
    2. 用固定输入或更短程序稳定复现。
    3. 确认第一次不匹配发生在哪个周期、哪一级。
    4. 打印该级的 valid、PC、指令和写使能。
    5. 仍看不清时，再为这个用例打开 VCD。

    分模块测试可以让失败信息对应到较小的代码范围。模块测试通过后，再进行流水线级和程序级测试。
