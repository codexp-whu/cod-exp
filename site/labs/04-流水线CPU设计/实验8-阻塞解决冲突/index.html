    实验8：阻塞技术解决相关引发的冲突¶

    原书参考

    《CPU设计实战：LoongArch版》5.1.2 实践任务8：阻塞技术解决相关引发的冲突

    实验目标¶

    • 实现数据相关检测逻辑，找出会读到旧值的指令对。
    • 用阻塞（stall / 插入气泡） 消解冲突：让后继指令在译码级等待。
    • func 测试在流水线 CPU 上第一次完全通过。

    知识背景¶

    相关检测¶

    阻塞的依据是数据相关：后一条指令的源寄存器，恰是前面还在流水线中、尚未写回的指令的目的寄存器。检测逻辑只需比较：

    • ID 级指令的源寄存器号 vs EX/MEM/WB 级正在流转的目的寄存器号；
    • 还需排除两种情况：该前级指令不写寄存器（如 store）、目的寄存器是 r0。
    需阻塞 ⟺ ∃ 级别 s ∈ {EX, MEM, WB}: 该级将写回 rd ≠ r0 ∧ rd = ID 级的 rs1 或 rs2

    阻塞的实现¶

    检测到相关时：

    1. 冻结 PC 和 IF/ID 寄存器——取指、译码停在原地；
    2. 向 EX 级注入气泡——把 ID/EX 寄存器清成"空操作"控制信号，让它流下去而不产生副作用。

    被阻塞的指令原地踏步若干拍后，等到前面的指令写回，即可读到正确值。

    代价¶

    每次阻塞损失一拍性能。本实验以正确性优先，阻塞条件的判定宁可保守（多阻塞不错），后续实验 9 再用前递把性能抢回来。

    任务要求¶

    1. 实现相关检测逻辑与流水线阻塞控制（PC 冻结、气泡注入）；
    2. func 测试完全通过；
    3. 统计测试程序中的阻塞次数，分析哪些指令组合贡献了主要阻塞。

    验收标准¶

    • func 测试全部通过；
    • 相关检测逻辑正确：不漏检（导致错误），也不过度保守（明显不该阻塞的场景也阻塞）；
    • 提交源码与实验报告，报告含阻塞次数统计与分析。

    思考题

    1. 为什么必须同时冻结 PC 和 IF/ID 寄存器，只冻结一个会怎样？
    2. load 指令后紧跟使用其结果的指令（load-use 相关），最少需要阻塞几拍？为什么单靠阻塞很难避开这一拍？
