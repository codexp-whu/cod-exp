    流水线CPU串讲

    Tip

    到这里，语法你已经学齐了，各个部件（PC、译码器、ALU、寄存器堆、流水线寄存器、转发、冒险控制）在"CPU 开发场景"一节里也都见过。但那些是零件，这一节我们要做的是把它们装成一台完整的机器。

    这一节不再引入新语法，而是带你从头到尾走一遍五级流水线 CPU 的顶层数据通路，看清数据是怎么在五级之间流动、控制信号是怎么串起来的。读完你应该建立起"全局观"——知道每个零件装在哪、和谁相连。建议对照着"CPU 开发场景"一节一起看。

    先说清楚：这是一份"骨架"，不是可以直接交的完整代码

    下面的代码为了讲清结构，简化/省略了不少细节（异常处理、完整指令集、部分边界情况）。它的作用是给你一张清晰的装配图，帮你理解各级如何咬合。真正实现时，你需要把每个模块的内部逻辑补全、把指令集补齐、把每个场景测充分。别指望复制粘贴就能跑通——动手把它补全、调通的过程，才是这门课真正要练的。

    先看全景：五级流水线长什么样¶

    经典的 RISC-V 五级流水线把一条指令的执行拆成五个阶段，每个阶段占一个时钟周期，相邻阶段之间用流水线寄存器隔开：

       IF          ID          EX          MEM         WB
 取指   →→→   译码   →→→   执行   →→→   访存   →→→   写回
   │           │           │           │           │
 [PC]        [译码器]     [ALU]       [DMem]      [写回选择]
 [IMem]      [寄存器堆读]  [转发Mux]              [寄存器堆写]
   │           │           │           │           │
   └─IF/ID─────┴─ID/EX─────┴─EX/MEM────┴─MEM/WB─────┘
     寄存器      寄存器       寄存器       寄存器
    • IF（取指）：用 PC 从指令存储器取出一条指令。
    • ID（译码）：解析指令，读寄存器堆，生成控制信号和立即数。
    • EX（执行）：ALU 做运算（算术、比较、算地址、判断分支）。
    • MEM（访存）：load/store 访问数据存储器。
    • WB（写回）：把结果写回寄存器堆。

    数据像流水线上的产品一样，每个周期往前挪一级。理想情况下，五级同时各处理一条指令，吞吐率是单周期的接近 5 倍——这正是流水线的意义。

    两大麻烦：相关与冒险

    流水线不是免费的午餐。因为多条指令同时在跑，会出现两类问题，它们是这一节的重点，也是流水线 CPU 真正难的地方：

    • 数据相关：后一条指令要用前一条还没写回的结果。解决办法：转发（Forwarding），把结果提前从中间级"抄近道"送过去。
    • 冒险（Hazard）：转发也救不了的情况（load 指令的结果本周期还没从内存拿到）用暂停（Stall）；分支跳转导致already取错的指令用冲刷（Flush）。

    把这两件事处理干净，你的流水线才能既快又对。

    顶层模块的整体骨架¶

    我们把整颗 CPU 写成一个 Core 模块，里面例化各个子模块（译码器、ALU、寄存器堆等），并声明四组流水线寄存器把五级串起来。先看骨架，再逐级填内容：

    import chisel3._
import chisel3.util._

class Core extends Module {
  val io = IO(new Bundle {
    // 和外部指令/数据存储器的接口（这里为简化，直接内置存储器）
    val debug_pc  = Output(UInt(32.W))   // 方便测试观察
  })

  // ========== 子模块例化 ==========
  val regfile = Module(new RegFile)     // 寄存器堆
  val decoder = Module(new Decoder)     // 译码器
  val alu     = Module(new Alu)         // ALU
  val imem    = SyncReadMem(4096, UInt(32.W))   // 指令存储器
  val dmem    = SyncReadMem(4096, UInt(32.W))   // 数据存储器

  // ========== 四组流水线寄存器 ==========
  // 每组都用 "wire 存本级算出的值，reg 打一拍传给下一级" 的模式
  val if2id_wire  = Wire(new IF2ID);   val if2id_reg  = RegInit(0.U.asTypeOf(new IF2ID))
  val id2ex_wire  = Wire(new ID2EX);   val id2ex_reg  = RegInit(0.U.asTypeOf(new ID2EX))
  val ex2mem_wire = Wire(new EX2MEM);  val ex2mem_reg = RegInit(0.U.asTypeOf(new EX2MEM))
  val mem2wb_wire = Wire(new MEM2WB);  val mem2wb_reg = RegInit(0.U.asTypeOf(new MEM2WB))

  // ========== 五级逻辑（下面逐级展开） ==========
  // IF  级：...
  // ID  级：...
  // EX  级：...
  // MEM 级：...
  // WB  级：...

  // ========== 冒险控制（stall / flush） ==========
  // ...
}

    记住这个"一 wire 一 reg"的套路

    每一级流水线寄存器都是一对：xxx_wire 装本级组合逻辑算出来的新值，xxx_reg 是打一拍之后、供下一级使用的值。默认情况下 xxx_reg := xxx_wire 让数据自然往前流；需要 stall/flush 时，我们再改写这几条赋值（本节最后详解）。

    这就是"CPU 开发场景"里 RegInit(0.U.asTypeOf(new ID2EX)) 那行的威力——十几个信号的流水线寄存器，一行声明，一行推进。

    IF 级：取指¶

    IF 级只做一件事：拿 PC 去 IMem 取指令，同时算好下一个 PC。

    // ---------- IF 级 ----------
val pc = RegInit("h00000000".U(32.W))    // 程序计数器

// 取指：同步读，指令下一拍才到（正好被 IF/ID 寄存器这一拍吸收）
val inst = imem.read(pc >> 2)

// 默认下一条 PC = PC + 4（顺序执行）；跳转时会被 EX 级覆盖（见后）
val pcPlus4 = pc + 4.U
val nextPC  = Wire(UInt(32.W))
nextPC := pcPlus4                          // 默认顺序，后面分支逻辑会改写它
pc := nextPC

// 把 pc 和 inst 交给 IF/ID 寄存器
if2id_wire.pc   := pc
if2id_wire.inst := inst

io.debug_pc := pc

    SyncReadMem 的"晚一拍"正好合流水线的拍

    imem.read 是同步读，PC 给出去、指令下一个周期才回来。在流水线里这不是问题——反而天然契合：这一拍取指，下一拍指令恰好落进 ID 级。这也是为什么大存储器用 SyncReadMem 而非组合读的 Mem。

    ID 级：译码 + 读寄存器¶

    ID 级从 IF/ID 寄存器拿到指令，做三件事：拆出寄存器编号、读寄存器堆、生成控制信号和立即数。

    // ---------- ID 级 ----------
val id_inst = if2id_reg.inst
val id_rs1  = id_inst(19, 15)     // 从指令里拆出源/目标寄存器编号
val id_rs2  = id_inst(24, 20)
val id_rd   = id_inst(11, 7)

// 译码器：输入指令，输出控制信号
decoder.io.inst := id_inst
val ctrl = decoder.io.ctrl        // 控制信号组（一个 Bundle，见下）

// 读寄存器堆（组合读，本周期就拿到）
regfile.io.rs1 := id_rs1
regfile.io.rs2 := id_rs2

// 立即数（根据指令类型拼装，逻辑见"CPU 开发场景 - 立即数生成器"）
val id_imm = ImmGen(id_inst, ctrl.immType)

// 把这一级的成果打包送进 ID/EX 寄存器
id2ex_wire.pc       := if2id_reg.pc
id2ex_wire.rs1Data  := regfile.io.rdata1
id2ex_wire.rs2Data  := regfile.io.rdata2
id2ex_wire.imm      := id_imm
id2ex_wire.rd       := id_rd
id2ex_wire.rs1      := id_rs1     // 保留编号，EX 级转发要用
id2ex_wire.rs2      := id_rs2
id2ex_wire.ctrl     := ctrl       // 整组控制信号一次传递

    为什么要把 rs1/rs2 编号也往下传？

    EX 级做转发时，需要判断"当前指令的源寄存器"是不是"前面指令的目标寄存器"。所以源寄存器编号 rs1/rs2 必须跟着指令一路传到 EX 级，供转发单元比对。这就是 ID2EX Bundle 里除了 rs1Data（寄存器的值）还要有 rs1（寄存器的编号）的原因。

    EX 级：转发 + ALU 执行¶

    EX 级是流水线里最"热闹"的一级：先做转发选择（决定 ALU 的两个输入到底从哪来），再用 ALU 算，最后处理分支。

    第一步：转发单元¶

    // ---------- EX 级：转发 ----------
// forwardA/B: 00=用寄存器原值, 01=从 EX/MEM 转发, 10=从 MEM/WB 转发
val forwardA = WireDefault(0.U(2.W))
val forwardB = WireDefault(0.U(2.W))

// rs1 的转发判断（优先用更近的 EX/MEM 级结果）
when(ex2mem_reg.ctrl.regWrite && ex2mem_reg.rd =/= 0.U &&
     ex2mem_reg.rd === id2ex_reg.rs1) {
  forwardA := 1.U
}.elsewhen(mem2wb_reg.ctrl.regWrite && mem2wb_reg.rd =/= 0.U &&
           mem2wb_reg.rd === id2ex_reg.rs1) {
  forwardA := 2.U
}

// rs2 的转发判断（同理）
when(ex2mem_reg.ctrl.regWrite && ex2mem_reg.rd =/= 0.U &&
     ex2mem_reg.rd === id2ex_reg.rs2) {
  forwardB := 1.U
}.elsewhen(mem2wb_reg.ctrl.regWrite && mem2wb_reg.rd =/= 0.U &&
           mem2wb_reg.rd === id2ex_reg.rs2) {
  forwardB := 2.U
}

// 写回级最终要写的值（WB 级会算，这里提前引用，见 WB 级）
val wbData = Wire(UInt(32.W))

// 根据转发选择，决定 ALU 两个操作数的真正来源
val fwdA = MuxLookup(forwardA, id2ex_reg.rs1Data)(Seq(
  1.U -> ex2mem_reg.aluResult,   // 从 EX/MEM 抄
  2.U -> wbData,                 // 从 MEM/WB 抄
))
val fwdB = MuxLookup(forwardB, id2ex_reg.rs2Data)(Seq(
  1.U -> ex2mem_reg.aluResult,
  2.U -> wbData,
))

    转发在"抄"什么？

    数据相关的本质是：前一条指令的结果算出来了（在 EX/MEM 或 MEM/WB 寄存器里躺着），但还没写回寄存器堆，而后一条指令已经读了寄存器堆、拿到的是旧值。转发就是绕过寄存器堆，把新结果直接从中间级"抄"到 ALU 输入端，省去等它写回再读出的两三拍。

    优先级 EX/MEM > MEM/WB：如果两级都命中同一个寄存器，要用更新（更近）的那个，也就是 EX/MEM 级。所以代码里用 when...elsewhen，EX/MEM 的判断在前。

    第二步：ALU 运算与分支¶

    // ---------- EX 级：ALU ----------
// ALU 的第二个操作数：R 型用寄存器值，I 型/load/store 用立即数
val aluB = Mux(id2ex_reg.ctrl.aluSrc, id2ex_reg.imm, fwdB)

alu.io.a  := fwdA
alu.io.b  := aluB
alu.io.op := id2ex_reg.ctrl.aluOp
val aluResult = alu.io.out

// 分支/跳转判断
val branchTaken = id2ex_reg.ctrl.isBranch && alu.io.zero   // 例：BEQ 看 zero 标志
val branchTarget = id2ex_reg.pc + id2ex_reg.imm

// 把 EX 级成果送进 EX/MEM 寄存器
ex2mem_wire.aluResult := aluResult
ex2mem_wire.storeData := fwdB          // store 要写内存的数据（注意也用转发后的值！）
ex2mem_wire.rd        := id2ex_reg.rd
ex2mem_wire.ctrl      := id2ex_reg.ctrl

    store 的数据也要走转发

    容易漏的一点：sw x5, 0(x6) 里，要写进内存的是 x5 的值。如果 x5 恰好是前一条指令刚算出来的，它也存在数据相关，同样需要转发。所以上面 ex2mem_wire.storeData := fwdB 用的是转发后的 fwdB，而不是 id2ex_reg.rs2Data。这类细节，正是自己动手调试时最容易踩的坑。

    MEM 级：访存¶

    MEM 级只有 load/store 指令真正干活，其余指令这一级"路过"，把 ALU 结果原样往下传。

    // ---------- MEM 级 ----------
val memAddr = ex2mem_reg.aluResult

// store：写内存
when(ex2mem_reg.ctrl.memWrite) {
  dmem.write(memAddr >> 2, ex2mem_reg.storeData)
}
// load：读内存（同步读，下一拍到）
val memData = dmem.read(memAddr >> 2)

// 送进 MEM/WB 寄存器
mem2wb_wire.aluResult := ex2mem_reg.aluResult
mem2wb_wire.memData   := memData
mem2wb_wire.rd        := ex2mem_reg.rd
mem2wb_wire.ctrl      := ex2mem_reg.ctrl

    WB 级：写回¶

    WB 级决定"到底把什么值写回寄存器堆"——是 ALU 的结果，还是从内存读来的数据。

    // ---------- WB 级 ----------
// memToReg=1 表示 load 指令，写回内存数据；否则写回 ALU 结果
wbData := Mux(mem2wb_reg.ctrl.memToReg, mem2wb_reg.memData, mem2wb_reg.aluResult)

// 写回寄存器堆
regfile.io.wen   := mem2wb_reg.ctrl.regWrite
regfile.io.rd    := mem2wb_reg.rd
regfile.io.wdata := wbData

    "写在前、读在后"的经典处理

    还有一种数据相关：WB 级正在写 x5，同一拍 ID 级正在读 x5。常见做法是让寄存器堆内部做"写优先"（同周期写的值直接旁路给读端口），或者干脆让写发生在时钟上升沿、读是组合逻辑，从而这一拍读到的还是旧值、靠转发补上。实现时你要想清楚自己的寄存器堆是哪种行为——这也是必须写测试专门验证的点。

    冒险控制：Stall 与 Flush¶

    最后，把 stall 和 flush 逻辑加上，它决定了那几组流水线寄存器到底是正常推进、保持、还是清零。这是整颗 CPU 逻辑上最精妙的部分。

    // ---------- 冒险控制 ----------
// (1) Load-use 冒险：EX 级是 load，且它的目标寄存器正是 ID 级要用的源寄存器
//     → 转发来不及（数据还没从内存读出），只能暂停一拍
val loadUseHazard = id2ex_reg.ctrl.memRead && id2ex_reg.rd =/= 0.U &&
  (id2ex_reg.rd === id_rs1 || id2ex_reg.rd === id_rs2)

// (2) 分支跳转：EX 级确定要跳，之前顺序取的两条指令是错的 → 冲刷
val doJump = branchTaken || id2ex_reg.ctrl.isJump

// 默认：各级正常往前推进
if2id_reg  := if2id_wire
id2ex_reg  := id2ex_wire
ex2mem_reg := ex2mem_wire
mem2wb_reg := mem2wb_wire

when(loadUseHazard) {
  // 暂停：PC 和 IF/ID 保持不动，往 ID/EX 里塞一个气泡（NOP）
  pc         := pc                            // PC 冻结
  if2id_reg  := if2id_reg                     // IF/ID 冻结
  id2ex_reg  := 0.U.asTypeOf(new ID2EX)       // 插入气泡
}

when(doJump) {
  // 冲刷：把已经错误取进来的两条指令清成气泡，PC 跳到目标
  nextPC := Mux(id2ex_reg.ctrl.isJump, aluResult, branchTarget)
  if2id_reg := 0.U.asTypeOf(new IF2ID)        // 冲刷 IF/ID
  id2ex_reg := 0.U.asTypeOf(new ID2EX)        // 冲刷 ID/EX
}

    气泡 = 全零 Bundle = 一条 NOP

    0.U.asTypeOf(new ID2EX) 把整个流水线寄存器清零，意味着 regWrite=0、memWrite=0……所有控制信号都为 0。这样的一"包"信号流到后面各级，什么副作用都不产生——这正是一条 NOP 指令的效果。用它填补暂停/冲刷留下的空档，既干净又不会遗漏某个控制位（对比 Verilog 里逐个信号清零，极易漏）。

    stall 和 flush 的优先级、边界，要靠测试反复打磨

    上面的控制逻辑是教学简化版。真实实现里还要考虑：跳转和暂停同一拍发生怎么办？PC 用 SyncReadMem 取指时暂停会不会取重复/丢指令？冲刷要冲几级？这些边界情况很难一次想全，标准做法就是：为每个冒险场景单独写测试（回顾上一节"CPU 测试的组织建议"），出错了看波形逐拍分析。把这些边界磨对，你的流水线才算真正立住。

    把控制信号也归拢进 Bundle¶

    你可能注意到上面反复出现 xxx.ctrl.regWrite、xxx.ctrl.aluOp——这就是"基本语法下"讲的 Bundle 嵌套。我们把一整组控制信号定义成一个 ControlSignals 子 Bundle，让它随指令在各级之间流动：

    class ControlSignals extends Bundle {
  val regWrite = Bool()      // 是否写回寄存器堆
  val memRead  = Bool()      // 是否读内存（load）
  val memWrite = Bool()      // 是否写内存（store）
  val memToReg = Bool()      // 写回的是内存数据(1)还是 ALU 结果(0)
  val aluSrc   = Bool()      // ALU 第二操作数用立即数(1)还是寄存器(0)
  val aluOp    = UInt(4.W)   // ALU 操作码
  val isBranch = Bool()      // 是否分支指令
  val isJump   = Bool()      // 是否无条件跳转
  val immType  = UInt(3.W)   // 立即数类型（I/S/B/U/J）
}

    于是每个流水线寄存器只需嵌一个 val ctrl = new ControlSignals，各级用 xxx_reg.ctrl.某信号 取用。将来要给某类新指令加一个控制位，只改这一个 Bundle，所有级自动携带——这正是 Chisel 相对 Verilog 在流水线开发中最爽的地方。

    怎么让它跑起来¶

    骨架装好后，按"仿真与测试"一节的方法验证。最实用的做法是灌一段小程序、跑若干周期、查寄存器：

    class CoreSpec extends AnyFlatSpec with ChiselScalatestTester {
  "Core" should "run a tiny program" in {
    // 假设 Core 提供了从文件加载 IMem 的方式，或在测试里预置几条指令
    test(new Core).withAnnotations(Seq(WriteVcdAnnotation)) { dut =>
      // 跑 50 个周期，让几条指令走完流水线
      dut.clock.step(50)
      // 检查 PC 是否推进到预期位置（更完整的测试会检查寄存器堆的值）
      // dut.io.debug_pc.expect(...)
    }
  }
}

    开发顺序建议

    1. 先搭无冒险的"裸流水线"：假装没有相关，五级直连，用互相无关的指令（如连续 addi 到不同寄存器）测通基本流动。
    2. 加转发：写一段有数据相关的程序（add x1,... 紧跟 add x2, x1, ...），验证 EX 转发正确。
    3. 加 load-use 暂停：lw 紧跟用它结果的指令，验证会正确暂停一拍。
    4. 加分支冲刷：带 beq/jal 的程序，验证跳转后错误指令被冲掉。
    5. 跑 riscv-tests 等回归测试收尾。

    每一步都建立在上一步测通的基础上。别跳步——跳步的代价是最后面对一个哪都可能错的黑箱。

    结语¶

    至此，从"为什么学 Chisel"，到语法，到测试，再到这一节把所有零件装成一台完整的流水线 CPU，整条学习路径就走完了。

    回头看，Chisel 帮你省掉的，正是 Verilog 里最磨人的那部分——几十上百根信号的重复连线、逐级复制的流水线寄存器、改一个信号要动好几处的痛苦。省下来的精力，你可以投到真正有含金量的地方：转发怎么设计更快、冒险怎么处理更省、流水线怎么切分更均衡。

    这，就是我们从 Chisel 重新出发的理由。 现在，去把你自己的流水线 CPU 搭起来吧——祝你玩得开心！
