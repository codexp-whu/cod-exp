    仿真与测试

    Tip

    上一节你已经能把 Chisel 变成 Verilog 了。但代码能生成 Verilog，不代表逻辑是对的。这一节我们讲怎么给电路写"测试"，在仿真里喂输入、看输出，确认它真的按你想的那样工作。

    对写 CPU 来说，这一节至关重要——一颗五级流水线 CPU 有几十条指令、转发、冒险、跳转，几乎不可能"一次写对"。没有一套顺手的测试方法，调试 CPU 会变成一场灾难。 学会测试，你才能一步步把 CPU 搭对。

    回忆你在 Verilog 里是怎么测的¶

    写单周期 CPU 时，你大概率写过一个 testbench：.v 文件里 initial 块给激励、$display 打印、$monitor 观察波形，再用 Vivado 仿真或 iverilog 跑。流程大致是：

    1. 手写激励（给输入信号赋值）
    2. 等一个时钟周期
    3. 检查输出对不对
    4. 出错了就打开波形图，一根信号一根信号地看

    Chisel 的测试思路完全一样，但用 Scala 代码来写激励和检查，比手写 Verilog testbench 简洁得多，而且能用上 Scala 的循环、断言、随机数。

    本讲义用哪种测试框架？

    Chisel 生态里测试有不止一种做法。本讲义采用 ChiselTest（chiseltest 库），因为它的 poke / peek / expect 接口对初学者最直观，也是国内课程和开源项目里最常见的选择。

    你可能还会听到更新的 ChiselSim（Chisel 6 内置的仿真接口）。两者概念完全相通——都是"喂输入、走时钟、查输出"，只是 API 名字略有差别。如果你的课程模板已经指定了某个框架，就用模板的那个；本讲义讲清楚 ChiselTest 的用法，换到 ChiselSim 你也能秒懂。

    ChiselTest 需要在 build.sbt 里引入（上一节的模板已经加好了）： 

    "edu.berkeley.cs" %% "chiseltest" % "6.0.0" % Test

    三个核心动作：poke / step / expect¶

    ChiselTest 的一切都围绕三个动作展开，记住它们你就掌握了测试的 80%：

    动作 含义 Verilog 类比
    poke 给一个输入端口赋值（喂激励） testbench 里 a = 8'd3;
    step 让时钟走 N 拍 #10;（等一个周期）
    peek / expect 读出一个输出端口的值 / 断言它等于期望值 $display / if (out !== ...) $error

    语法长这样：

    dut.io.a.poke(3.U)         // 给输入 a 喂 3
dut.io.b.poke(4.U)         // 给输入 b 喂 4
dut.clock.step()           // 时钟走 1 拍（括号里可写数字，如 step(5) 走 5 拍）
dut.io.sum.expect(7.U)     // 断言输出 sum 等于 7，不等就报错
val x = dut.io.sum.peek()  // 只读出 sum 的值，不做断言

    dut 是 "Device Under Test"（被测设备）的惯例简称，就是你正在测的那个模块实例。

    第一个测试：给加法器写 testbench¶

    继续用上一节的 Adder。把下面代码存为 src/test/scala/AdderSpec.scala：

    // src/test/scala/AdderSpec.scala
import chisel3._
import chiseltest._
import org.scalatest.flatspec.AnyFlatSpec

// 测试类：继承 AnyFlatSpec 和 ChiselScalatestTester
class AdderSpec extends AnyFlatSpec with ChiselScalatestTester {

  "Adder" should "correctly add two numbers" in {
    test(new Adder) { dut =>          // test(new 模块) { dut => ... }
      // 测试 3 + 4 = 7
      dut.io.a.poke(3.U)
      dut.io.b.poke(4.U)
      dut.io.sum.expect(7.U)          // 组合逻辑，喂完输入立刻能查输出

      // 测试 10 + 20 = 30
      dut.io.a.poke(10.U)
      dut.io.b.poke(20.U)
      dut.io.sum.expect(30.U)
    }
  }
}

    运行测试：

    sbt test

    如果逻辑正确，你会看到绿色的：

    [info] AdderSpec:
[info] Adder
[info] - should correctly add two numbers
[info] All tests passed.

    如果你故意把 expect(7.U) 改成 expect(8.U)，ChiselTest 会精确地告诉你哪里错了：

    Expectation failed: observed value 7 != 8

    这段代码的骨架，照抄就行

    初学别被 AnyFlatSpec、should、in 这些词吓到——它们来自 Scala 的测试库 ScalaTest，你不需要理解其原理，把它当固定模板套用即可：

    class 名字Spec extends AnyFlatSpec with ChiselScalatestTester {
  "被测模块" should "做什么" in {
    test(new 模块) { dut =>
      // 这里写 poke / step / expect
    }
  }
}

    随着测试变多，你只需不断往里加 "xxx" should "yyy" in { ... } 小节。

    组合逻辑 vs 时序逻辑：什么时候要 step¶

    这是初学者最容易困惑的点，务必分清：

    • 组合逻辑（如加法器、ALU、译码器）：输出只由当前输入决定。poke 完输入，立刻就能 expect 输出，不需要 step。
    • 时序逻辑（如带寄存器的计数器、PC、流水线）：输出要等下一个时钟沿才更新。poke 完输入后，必须 step() 走一拍，新值才会出现在寄存器输出上。

    看一个计数器的例子：

    class Counter extends Module {
  val io = IO(new Bundle {
    val en    = Input(Bool())
    val count = Output(UInt(8.W))
  })
  val cnt = RegInit(0.U(8.W))
  when(io.en) { cnt := cnt + 1.U }
  io.count := cnt
}

    测试它：

    class CounterSpec extends AnyFlatSpec with ChiselScalatestTester {
  "Counter" should "count up when enabled" in {
    test(new Counter) { dut =>
      dut.io.en.poke(true.B)
      dut.io.count.expect(0.U)    // 复位后是 0，此刻还没走时钟

      dut.clock.step()            // 走一拍
      dut.io.count.expect(1.U)    // 现在寄存器更新为 1

      dut.clock.step()
      dut.io.count.expect(2.U)    // 再走一拍变 2

      dut.io.en.poke(false.B)     // 关掉使能
      dut.clock.step()
      dut.io.count.expect(2.U)    // 保持不变，不再增加
    }
  }
}

    时序逻辑测试的黄金法则

    对寄存器/时序电路，顺序永远是：先 poke 好这一拍的输入 → 再 step() → 然后 expect 下一拍的输出。

    如果你 poke 完输入不 step 就去 expect 寄存器的输出，读到的会是旧值，测试结果会让你一头雾水。记住："寄存器的值要过了时钟沿才更新"，这在测试里同样成立。

    用 Scala 的力量写更聪明的测试¶

    手写一堆 poke/expect 很枯燥。既然测试也是 Scala 代码，就能用循环、随机数把测试写得又短又全面。

    用循环批量测试¶

    test(new Adder) { dut =>
  // 遍历一堆输入组合，自动比对
  for (a <- 0 until 20; b <- 0 until 20) {
    dut.io.a.poke(a.U)
    dut.io.b.poke(b.U)
    dut.io.sum.expect((a + b).U)     // 期望值直接用 Scala 算出来
  }
}

    一个双重 for 循环就覆盖了 400 组输入——这在 Verilog testbench 里要写得痛苦得多。

    用随机数做"拷机测试"¶

    import scala.util.Random

test(new Adder) { dut =>
  for (_ <- 0 until 1000) {
    val a = Random.nextInt(256)      // 0~255 随机
    val b = Random.nextInt(256)
    dut.io.a.poke(a.U)
    dut.io.b.poke(b.U)
    dut.io.sum.expect(((a + b) & 0xff).U)   // 注意 8 位会溢出回绕，用 &0xff
  }
}

    peek 出来的值怎么用

    peek() 返回的是 Chisel 类型，想拿它和 Scala 数值比较，用 .litValue： 

    val out = dut.io.sum.peek().litValue    // 转成 Scala 的 BigInt
println(s"sum = $out")
if (out != 7) println("对不上！")
    不过大多数时候直接用 expect 更省事，它自动帮你比对并报错。

    看波形：调试的终极手段¶

    expect 告诉你"错了"，但为什么错往往要看波形。ChiselTest 可以在跑测试时导出 VCD 波形文件，用 GTKWave、Surfer 等工具打开。

    给 test(...) 加上 .withAnnotations(Seq(WriteVcdAnnotation))：

    import chiseltest._

test(new Counter).withAnnotations(Seq(WriteVcdAnnotation)) { dut =>
  dut.io.en.poke(true.B)
  dut.clock.step(10)
}

    跑完后，波形文件会生成在 test_run_dir/ 目录下的对应子文件夹里（.vcd 文件）。用 GTKWave 打开就能看到每根信号随时钟变化的波形，和你在 Vivado 里看仿真波形一样。

    调 CPU 时，先 printf，再看波形

    调试流水线 CPU 的推荐节奏：

    1. 先靠 expect 断言定位到"第几条指令、哪一级出错"——比如写一段测试程序，检查若干周期后寄存器堆里的值对不对。
    2. 在关键位置撒 printf（见上一册"调试手段"一节），把每一级的 pc、指令、控制信号打出来，先用日志缩小范围。
    3. 实在看不出来再开波形，WriteVcdAnnotation 导出 VCD，盯着出问题那一级的信号逐拍分析。

    波形信息量最大但也最费眼，通常放到最后用。

    换用 Verilator 后端跑得更快（可选）¶

    ChiselTest 默认用一个纯软件的仿真器（Treadle/内置仿真），对小模块够用。但 CPU 规模一大、跑的指令一多，就会慢。这时可以切换到 Verilator 后端——它把电路编成 C++ 再跑，快很多：

    test(new MyCPU).withAnnotations(Seq(VerilatorBackendAnnotation)) { dut =>
  // ...
}

    Verilator 需要单独安装

    用 Verilator 后端前，你的系统里得先装好 verilator 命令（各平台包管理器都能装，如 apt install verilator / brew install verilator）。初学阶段用默认后端即可，等 CPU 跑大程序嫌慢了再换。

    CPU 测试的组织建议¶

    写整颗 CPU 时，别指望一个测试搞定，按"由小到大"分层测：

    阶段 测什么 怎么测
    单元测试 ALU、译码器、立即数生成器等单个模块 给定输入，expect 输出。穷举或随机
    通路测试 寄存器堆读写、单条指令走完全程 造一两条指令，检查结果寄存器
    集成测试 一小段汇编程序（含相关、跳转） 把程序 hex 加载进 IMem，跑若干周期，检查最终寄存器/内存状态
    回归测试 官方测试集（如 riscv-tests） 批量跑，全绿才算过

    先让"一条指令"跑通，再谈流水线

    刚搭 CPU 时，别一上来就灌整个测试程序。先写测试让单独一条 addi 正确执行、正确写回，再逐步加指令、加相关场景。每加一个特性就补一个测试，出问题时你立刻知道是刚才那点改动引入的——这比写完几百行再一起调要高效得多。

    本节小结¶

    // 你需要记住的全部核心 API：
test(new 模块) { dut =>
  dut.io.输入.poke(值)          // 喂输入
  dut.clock.step(n)            // 走 n 拍时钟（组合逻辑可省略）
  dut.io.输出.expect(期望值)     // 断言输出
  dut.io.输出.peek().litValue   // 读出输出值（转成 Scala 数）
}
// 加波形：test(new 模块).withAnnotations(Seq(WriteVcdAnnotation)) { ... }
// 运行：sbt test（或 sbt 交互式里 ~test 自动重跑）

    有了生成 Verilog 的能力（上一节）和验证逻辑的能力（这一节），你已经具备了独立开发的完整闭环。接下来的语法章节里，每学一个模块，都建议你顺手写个小测试跑一跑——把知识立刻变成能跑的电路，是最扎实的学习方式。
