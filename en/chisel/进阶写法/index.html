    Advanced Features¶

    This section is not a prerequisite for the basic five-stage pipeline. On a first reading you can just get to know Decoupled; the rest can be consulted once the CPU's basic functionality is working.

    The Decoupled Handshake¶

    In a pipelined CPU, data cannot move between adjacent stages every single cycle.

    A load-use hazard needs a stall and a jump needs a flush; the cache and the bus may also have unpredictable latency. The Chisel standard library uses DecoupledIO as a uniform way to express the ready/valid handshake, but the protocol will not handle branch flushing or pipeline state for you.

    In the pipeline example above, stalls and flushes are controlled by conditional connections on the stage registers. When you connect modules that have wait states, such as the I-Cache or the data bus, you also need a uniform way to say "is this request valid" and "can the other end accept it". DecoupledIO provides that set of handshake signals.

    The Three Parts of DecoupledIO¶

    // DecoupledIO 的简化定义（在 chisel3.util 中）
class DecoupledIO[T <: Data](gen: T) extends Bundle {
    val ready = Input(Bool())    // 接收方说"我可以收了"
    val valid = Output(Bool())   // 发送方说"我有数据要传"
    val bits  = Output(gen)      // 实际数据（类型为泛型 T）
}

    A successful transfer happens on the clock edge where ready && valid are both true — what is usually called fire.

    Once the producer raises valid, it should hold valid and bits steady until the transfer completes. Otherwise, if the consumer applies backpressure, the data being waited on may change.

    Decoupled defines only the interface protocol

    DecoupledIO provides ready, valid, bits, and a few related helper methods. Whether the producer really holds its data steady, whether the queue is deep enough, and how requests on an error path are canceled are still up to you as the designer.

    Basic Usage¶

    // 生产者：声明 Decoupled 输出端口
class Producer extends Module {
    val io = IO(new Bundle {
        val out = Decoupled(UInt(32.W))
    })
    val dataReg = RegInit(0.U(32.W))

    io.out.bits  := dataReg
    io.out.valid := true.B

    when(io.out.fire) { dataReg := dataReg + 1.U }
}

    // 消费者：声明 Decoupled 输入端口
class Consumer extends Module {
    val io = IO(new Bundle {
        val in     = Flipped(Decoupled(UInt(32.W)))
        val enable = Input(Bool())
    })
    val dataReg = RegInit(0.U(32.W))
    io.in.ready := io.enable

    when(io.in.fire) {
        dataReg := io.in.bits
    }
}

    What Flipped does: Decoupled defaults to the "output" orientation (ready as an input, valid/bits as outputs).

    A consumer needs the opposite: ready as an output and valid/bits as inputs. Flipped flips the whole orientation in one go, with no need to rewrite the Input/Output of all three fields by hand.

    fire()¶

    DecoupledIO provides several convenience methods; fire among them means that ready and valid are both high, that is, the transfer succeeded:

    io.out.ready
io.out.valid
io.out.bits
io.out.fire   // 等价于 io.out.ready && io.out.valid

    The common pattern on the producer side:

    // 典型的 Decoupled 生产者：fire 后更新下一笔数据
when(io.out.fire) {
    // 上一笔数据已被接收，准备下一笔
    dataReg := nextData
}

    A data source of finite length can add a validReg; you lower it once the last item has been sent.

    Bulk Connection with <>¶

    Chisel provides the <> operator for connecting two Bundles of the same structure in bulk:

    producer.io.out <> consumer.io.in
// 等价于：
// consumer.io.in.ready -> producer.io.out.ready
// producer.io.out.valid -> consumer.io.in.valid
// producer.io.out.bits  -> consumer.io.in.bits

    <> matches fields by name and connects them according to their Input/Output directions. Interfaces whose structure and directions are compatible can be connected as a whole, with no need to write := field by field.

    Queue¶

    Queue inserts a FIFO between producer and consumer and propagates backpressure:

    val producer = Module(new Producer)
val consumer = Module(new Consumer)

consumer.io.in <> Queue(producer.io.out, 2)

    When you need other behavior, switch to the parameterized version rather than keeping the connection above as well:

    consumer.io.in <> Queue(
    producer.io.out,
    entries = 4,        // FIFO 深度
    pipe    = true,
    flow    = false
)

    The basic behavior is as follows:

    • when the consumer's ready=0, data is buffered in the queue
    • when the queue is full, the producer sees ready=0 and pauses automatically
    • when the queue is empty, the consumer sees valid=0 and knows there is no data available

    flow = true lets the input pass combinationally straight through to the output when the queue is empty; pipe = true lets an enqueue proceed when the queue is full but an item is dequeued in the same cycle. Both change the combinational path of ready/valid, so neither should be thought of simply as an extra pipeline register. Whether they improve timing depends on the particular connection and on the synthesis result.

    Pipe¶

    Pipe works on ValidIO: it delays only valid and bits, and has no ready and no backpressure:

    val staged1 = Pipe(io.in)
val staged3 = Pipe(io.in, latency = 3)

    It suits a delay path where the consumer can accept data every cycle. If the downstream side may pause, use DecoupledIO with Queue — Pipe is not a substitute.

    Choosing between a plain Bundle and Decoupled

    Situation What to use Why
    Between pipeline stages (there are stalls/flushes, and the control logic must be exact for every cycle) a plain Bundle + manual when control hold, clear, and normal update are described separately
    Fetch ↔ I-Cache, memory access ↔ bus DecoupledIO the request may have to wait, so a ready/valid handshake is needed
    Between two modules with mismatched rates DecoupledIO + Queue the Queue buffers data the downstream side has not accepted yet
    One-way push, no backpressure needed (e.g. interrupt signals, branch prediction results) ValidIO (see the next section) the interface contains no ready

    For the basic five-stage pipeline, use plain Bundles for the inter-stage registers and handle stall/flush manually. Reach for Decoupled when connecting modules that may wait, such as the cache or the bus.

    Other Common Construction Primitives¶

    Besides Mux, RegInit, and Bundle, chisel3.util offers other everyday components such as ValidIO, Counter, ShiftRegister, and Arbiter. Their interfaces and the conditions under which they apply are described below.

    ValidIO¶

    ValidIO has only valid and bits, no ready. It suits one-way paths where the consumer can always accept data and no backpressure is needed.

    // ValidIO 的定义（在 chisel3.util 中）
class ValidIO[T <: Data](gen: T) extends Bundle {
    val valid = Output(Bool())
    val bits  = Output(gen)
}

    // 生产者：声明 Valid 输出
class BranchPredictor extends Module {
    val io = IO(new Bundle {
        val prediction = Valid(UInt(32.W))   // 预测的目标地址 + 是否有效
    })
    io.prediction.bits  := predictedTarget
    io.prediction.valid := hasPrediction     // 没有预测时 valid=0，bits 值无效
}

// 消费者：取指单元检查 valid 决定是否跳转
val pc_next = Mux(predictor.io.prediction.valid,
                  predictor.io.prediction.bits,
                  pc + 4.U)
    Situation What to use Reason
    The consumer may be unable to accept, so backpressure is needed DecoupledIO the consumer can hold off the transfer via ready
    The consumer can always accept, and only data and a valid flag are passed ValidIO the interface contains no ready

    Counter¶

    Counter implements a counter and packages up the common pattern of counting conditionally and wrapping around when the limit is reached:

    // Counter(cond, n)：cond 为 true 时计数 +1，计到 n-1 后下一个周期回 0
val (count, wrap) = Counter(true.B, 32)        // 每周期 +1，0→31→0→31→...
val (count, wrap) = Counter(en, 100)           // 有条件计数

// count: UInt —— 当前计数值（0 到 n-1）
// wrap:  Bool —— 当 count === n-1 且 cond 为 true 时为真

    Iteration counting in a multi-cycle divider:

    val (cycle, done) = Counter(state === RUN, 32)  // RUN 状态每周期 +1

when(state === RUN) {
    // 迭代除法算法的每一步
    remainder := remainder - divisor
    // ...
    when(done) { state := DONE }   // 32 个周期后完成
}

    Compare with the hand-written version:

    // 手写版本容易忘记 wrap 条件判断的细节
val cycle = RegInit(0.U(5.W))
when(state === RUN) {
    cycle := cycle + 1.U
}
val done = cycle === 31.U && state === RUN

// Counter 版本意图更清晰，且自动处理位宽
val (cycle, done) = Counter(state === RUN, 32)

    Counter infers the bit width for you

    In Counter(cond, n), n is a Scala Int, and count takes the bit width log2Ceil(n), enough to represent 0 to n-1.

    ShiftRegister¶

    ShiftRegister gives you a multi-cycle delay: it is equivalent to several RegNexts chained together, plus an optional enable signal:

    // ShiftRegister(in, n)：将 in 延迟 n 拍
val delayed = ShiftRegister(io.in, 3)
// 等价于：
// val delayed = RegNext(RegNext(RegNext(io.in)))

// ShiftRegister(in, n, en)：带使能的版本——en=1 时移位，en=0 时保持
val delayed = ShiftRegister(io.in, 3, en)
// 等价于 3 个带使能的 RegEnable 串联

// ShiftRegister(in, n, resetData, en)：额外指定复位值
val delayed = ShiftRegister(io.in, 3, 0.U, en)

    A typical case in the CPU — keeping a control signal aligned with data that has been delayed:

    // EX 阶段计算出的 aluResult 经过 MEM→WB 两级才写回
// regWrite 标志也需要打同样的拍数，保持与数据同步
val regWrite_mem = RegNext(regWrite_ex)
val regWrite_wb  = RegNext(regWrite_mem)

// 用 ShiftRegister 一行搞定
val regWrite_delayed = ShiftRegister(regWrite_ex, 2)   // 打 2 拍，对齐到 WB

    Arbiter: the Many-to-One Scheduler¶

    When several requesters compete for the same resource (two masters sharing a bus, say), the arbiter decides between them. chisel3.util provides two ready-made arbiters:

    val arb = Module(new Arbiter(UInt(32.W), 4))
arb.io.in(0) <> req0
arb.io.in(1) <> req1
arb.io.in(2) <> req2
arb.io.in(3) <> req3
arb.io.out <> sharedBus

    The round-robin arbiter has the same interface:

    val rrArb = Module(new RRArbiter(UInt(32.W), 4))

    Distinguishing Arbiter from RRArbiter

    Arbiter is a fixed-priority arbiter: when several inputs are valid at once it picks the lower-numbered one. RRArbiter uses a round-robin policy.

    Both have DecoupledIO on their inputs and on their output. A transfer completes when the selected requester has valid=1 and the output has ready=1; the round-robin arbiter then moves its starting point, while the fixed-priority arbiter still begins from the lowest-numbered valid request.

    Arbitration in a CPU

    A single-core teaching CPU will not necessarily need an Arbiter. When the I-Cache and D-Cache have to share one external bus interface, an arbiter can be used to select the current request.

    PriorityMux and PriorityEncoder¶

    PriorityEncoder returns the index of the highest-priority set bit, which by default means low bits first. PriorityMux selects the first value in a list whose condition holds.

    val irq = Wire(UInt(8.W))

// irq(0) 优先级最高，其次是 irq(1)
val irqNum = PriorityEncoder(irq)

    When irq is all zeros the encoded result is also zero, so you must check irq.orR separately to tell whether there really is a request.

    // PriorityMux: 按优先级选择——第一个满足条件的值被选中
val result = PriorityMux(Seq(
    (cond0) -> value0,    // 优先级最高——cond0 先被检查
    (cond1) -> value1,
    (cond2) -> value2     // 优先级最低
))

    PriorityMux, MuxCase, and Mux1H

    PriorityMux and MuxCase both express an ordered priority selection and do not require the conditions to be mutually exclusive. Only Mux1H assumes the select conditions are one-hot; if several are true at once, it ORs the candidate data together bit by bit.

    Parameterization and Code Generation¶

    Scala's constructor parameters, collections, and functions can be used to generate configurable hardware structures. Here are three patterns that come up often in this course's project.

    Generic Modules¶

    Put parameters such as bit width, depth, and count in the class constructor, and passing different values at instantiation gives you modules of different sizes:

    // 参数化 ALU：位宽可变
class Alu(width: Int) extends Module {
    val io = IO(new Bundle {
        val a   = Input(UInt(width.W))
        val b   = Input(UInt(width.W))
        val op  = Input(UInt(4.W))
        val out = Output(UInt(width.W))
    })
    io.out := MuxLookup(io.op, 0.U(width.W))(Seq(
        AluOp.ADD -> (io.a + io.b),
        AluOp.SUB -> (io.a - io.b),
        // ...
    ))
}

// 实例化 32 位和 64 位两种 ALU
val alu32 = Module(new Alu(32))
val alu64 = Module(new Alu(64))
// 两个实例使用相同结构，位宽参数不同

    // 参数化寄存器堆：寄存器数量和位宽都可配置
class RegFile(regCount: Int, xlen: Int) extends Module {
    val addrWidth = log2Ceil(regCount)
    val io = IO(new Bundle {
        val rs1 = Input(UInt(addrWidth.W))     // 地址位宽自动匹配寄存器数量
        val rs2 = Input(UInt(addrWidth.W))
        val rd  = Input(UInt(addrWidth.W))
        val wen = Input(Bool())
        val wdata = Input(UInt(xlen.W))
        val rdata1 = Output(UInt(xlen.W))
        val rdata2 = Output(UInt(xlen.W))
    })
    val rf = RegInit(VecInit(Seq.fill(regCount)(0.U(xlen.W))))
    io.rdata1 := Mux(io.rs1 === 0.U, 0.U, rf(io.rs1))
    io.rdata2 := Mux(io.rs2 === 0.U, 0.U, rf(io.rs2))
    when(io.wen && io.rd =/= 0.U) {
        rf(io.rd) := io.wdata
    }
}

    RV32 and RV64 both have 32 general-purpose integer registers; the difference is the data width:

    val rf32 = Module(new RegFile(32, 32))
val rf64 = Module(new RegFile(32, 64))

    Scala code runs at generation time

    Constructor parameters, log2Ceil, and Seq.fill are all Scala. if, for, and functions can decide the number of modules, the bit widths, and the wiring structure at generation time, but they never become control flow in the running hardware.

    Writing a Decode Table with BitPat¶

    Use the ? of BitPat for the "don't care" bits of instruction decoding, not the hardware value DontCare. The example below assumes InstType and AluOp are encoded as UInt; ListLookup can look up several control signals in one go:

    val default = List(InstType.ILLEGAL, AluOp.NOP, 0.U(1.W))

val table = Array(
  BitPat("b0000000??????????000?????0110011") ->
    List(InstType.ADD, AluOp.ADD, 1.U(1.W)),
  BitPat("b0100000??????????000?????0110011") ->
    List(InstType.SUB, AluOp.SUB, 1.U(1.W))
)

    After the lookup, give each result a name:

    val decoded = ListLookup(io.inst, default, table)

val instType = decoded(0)
val aluOp    = decoded(1)
val regWrite = decoded(2).asBool

    A table like this puts instruction bit patterns and control signals side by side. When you add an instruction you still have to add tests, and in particular you should check whether two BitPats could ever match at the same time.

    for / yield¶

    When the number of a module's ports or submodules is decided by a parameter, for / yield is the standard tool:

    val banks = Seq.fill(numBanks)(Module(new CacheBank(bankSize)))

banks.zipWithIndex.foreach { case (bank, i) =>
  bank.io.addr  := io.addr
  bank.io.wdata := io.wdata
  bank.io.wen   := io.wen && (bankSel === i.U)
}

    If the hit signals of the banks are guaranteed to be one-hot, you can select the read data directly:

    val choices = banks.map(bank => bank.io.hit -> bank.io.rdata)
io.rdata := Mux1H(choices)

    // 流水线延迟线：N 级参数化
class DelayLine[T <: Data](gen: T, stages: Int) extends Module {
    val io = IO(new Bundle {
        val in  = Input(gen)
        val out = Output(gen)
    })
    io.out := (0 until stages).foldLeft(io.in) { (sig, _) =>
        RegNext(sig)   // 每一级打一拍，共 stages 拍
    }
}

// 使用：生成一个 5 级延迟线
val delay = Module(new DelayLine(UInt(32.W), 5))

    Generating a cascade with foldLeft

    foldLeft is a higher-order function on Scala collections: it combines an initial value with each element of the collection in turn:

    // foldLeft 展开过程（以 stages=3 为例）
(0 until 3).foldLeft(io.in) { (sig, _) => RegNext(sig) }
// = RegNext(RegNext(RegNext(io.in)))

    foldLeft is well suited to generating repeated structures that chain one stage onto the next, such as delay lines or bypass selection chains. It folds in order and will not restructure the operation into a balanced tree.

    Counter, Queue, and parameterized modules can be used where the situation calls for them. Once the timing and behavior of your basic CPU are confirmed, use these components to tidy up repeated structure.
