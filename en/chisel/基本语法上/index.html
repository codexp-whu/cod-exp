    Basic Syntax (Part 1): Basic Data Types¶

    When moving from Verilog to Chisel, the first thing to sort out is when a line of Scala runs versus when a hardware signal changes. This chapter explains those two stages first, and then introduces the data types and signals you will use most often.

    Keeping the Two Stages Apart¶

    A piece of Chisel source goes through two stages.

    The first is the circuit generation stage. Mill runs the Scala program; Scala's class, if, for, and functions all execute at that point, and the end result is a hardware circuit diagram.

    The second is the hardware run stage. The generated SystemVerilog goes into a simulator or an FPGA, where combinational logic follows its inputs and registers update on the clock edge.

    What you see When it happens What it does
    Scala Int, Boolean, if, for While generating the circuit Decides which circuit gets generated
    Chisel UInt, Bool, when, Reg While the hardware runs Represents real signals and state

    A very small example:

    class Adder(val width: Int) extends Module {
  val io = IO(new Bundle {
    val a = Input(UInt(width.W))
    val b = Input(UInt(width.W))
    val y = Output(UInt(width.W))
  })

  io.y := io.a + io.b
}

    When you instantiate new Adder(32), the Scala parameter width is 32, and that is what decides to generate a 32-bit adder. Once generation has finished, there is no register called width in the hardware; io.a, io.b, and io.y are the signals that change at run time.

    A Scala condition is not a hardware condition

    The condition in if (debug) is usually a Scala Boolean: it decides whether a piece of hardware gets generated at all. The condition in when(io.enable) is a Chisel Bool, and it generates a circuit controlled by io.enable. Do not use a Scala if in place of a hardware multiplexer.

    Common Scala Syntax¶

    This section covers the Scala syntax you will keep coming back to when implementing a CPU; look up the rest when you need it.

    val, var, and :=¶

    val means the Scala name cannot be rebound; var means it can:

    val xlen = 32
var fileCount = 0
fileCount = fileCount + 1

    When declaring hardware you almost always use val:

    val pc = RegInit(0.U(32.W))
pc := pc + 4.U

    Here pc always refers to the same hardware register, so it is a val. What val restricts is the Scala name; the bits stored in the register still change on the clock edge.

    = and := also live at different levels:

    Syntax Meaning
    val nextPC = pc + 4.U Give a hardware expression a Scala name
    pc := nextPC Connect the hardware expression to the register input
    x = y Rebind a Scala var; not a hardware assignment

    Do not use var to model a register

    Scala rebinding only happens during generation. To hold data across cycles in hardware, you must use Reg or RegInit.

    class, new, and object¶

    class defines a structure you can create over and over. A Bundle is created with new, and a module instance additionally has to be wrapped in Module(...):

    class FetchPacket extends Bundle {
  val pc = UInt(32.W)
  val inst = UInt(32.W)
}

val packet = Wire(new FetchPacket)
val alu = Module(new Alu)

    object is a Scala singleton, a good place for global configuration and fixed encodings:

    object CoreConfig {
  val XLEN = 32
  val RESET_PC = BigInt("80000000", 16)
}

    Here XLEN and RESET_PC are both Scala constants used during generation. They do not generate any hardware of their own.

    Seq¶

    Seq is a Scala sequence, roughly a read-only list. It is not hardware itself, but it can hold Chisel expressions or module instances.

    val zeros = Seq.fill(32)(0.U(32.W))
val indices = Seq.tabulate(4)(i => i.U)
val adders = Seq.fill(2)(Module(new Adder(32)))

    When you later meet VecInit(Seq(...)) or MuxLookup(...)(Seq(...)), the outer Seq collects a number of items during generation, and Chisel then generates a circuit from those items.

    for Loops¶

    A for in Chisel is a Scala loop, and it unrolls during generation. The code below generates four copies of parallel addition logic:

    for (i <- 0 until 4) {
  io.out(i) := io.in(i) + 1.U
}

    It means roughly the same as writing four lines of connections by hand — not out(0) computed in cycle 0 and out(1) in cycle 1.

    Distinguish it from if in software programming

    A for in Chisel expresses parallelism; it is used to describe many copies of the same hardware structure.

    If you need a divider that iterates over cycles, use a state machine, a counter, and registers. A Scala for only replicates or organizes hardware; it does not produce multi-cycle behavior.

    yield collects the result of each iteration into a Seq:

    val incremented = for (i <- 0 until 4) yield {
  io.in(i) + 1.U
}

    Here incremented is a Scala sequence containing four hardware expressions.

    reduce¶

    reduce merges a sequence item by item into a single result. Given a Chisel operation, it generates the corresponding combinational logic.

    val sum = data.reduce(_ + _)
val anyHit = hitVec.reduce(_ || _)
val allReady = readyVec.reduce(_ && _)

    _ + _ is shorthand for an anonymous function, and reads as "add the running result to the current element". For example, data.reduce(_ + _) ends up wiring every element of data into an adder network.

    reduce says "merge all the elements", but it makes no promise of generating a balanced tree. When there are many inputs or the timing requirement is tight, check the generated RTL and the synthesis report.

    package and import¶

    Once CPU code is split across several files, you usually put it in one namespace with package. For example, mycpu/src/cpu/Alu.scala:

    package cpu

import chisel3._
import chisel3.util._

class Alu extends Module {
  // 端口与逻辑
}

    Files in the cpu package can use Alu directly. To reference it across packages, write:

    import cpu.Alu
import cpu.{Decoder, RegisterFile}

    For a five-stage pipeline CPU at the scale of this course's labs, you do not need a fine-grained package layout. Keeping the core modules together under the cpu package is usually clear enough to start with.

    Scala Types and Chisel Types¶

    The two groups of types below have similar names but different purposes:

    Scala data Chisel data Difference
    Int, BigInt UInt, SInt The former is computed during generation; the latter represents hardware bits
    Boolean Bool The former controls Scala; the latter can be wired into a circuit
    Seq[T] Vec[T] The former is indexed by a Scala index; the latter can be selected by a hardware index

    For example:

    val width: Int = 32
val resetPC: BigInt = BigInt("80000000", 16)

val data = Wire(UInt(width.W))
val valid = Wire(Bool())

    width and resetPC are already fixed when the circuit is generated; data and valid are the hardware signals you can see in a simulation waveform.

    Three Common Hardware Data Types¶

    Chisel syntax Meaning Closest Verilog equivalent
    UInt(32.W) 32-bit unsigned type logic [31:0]
    SInt(32.W) 32-bit signed two's-complement type logic signed [31:0]
    Bool() Single-bit boolean type logic

    These forms only describe a signal's type. It is only once you hand one to Wire, Reg, or IO that you get a hardware signal with an owner:

    val aluOut = Wire(UInt(32.W))
val pc = RegInit(0.U(32.W))

    You can also bind a hardware expression straight to a val, without writing an extra Wire for every intermediate result:

    val nextPC = pc + 4.U
val isZero = aluOut === 0.U

    nextPC and isZero still stand for hardware expressions; they simply have no separate Wire declared that could be connected more than once.

    Hardware Literals¶

    Only when you add .U, .S, or .B to a Scala number does it become a Chisel hardware constant:

    0.U(32.W)
"hff".U(32.W)
"b1010".U(4.W)
-3.S(8.W)
true.B
false.B

    The bit width of 0.U can be inferred from where it is connected, but reset values, interface constants, masks, and addresses should normally have an explicit bit width. The next chapter continues with the result bit width of arithmetic expressions.

    Always specify the bit width

    Always give a literal an explicit bit width when you define it in Chisel, or you will get hard-to-diagnose errors such as bit-width problems.

    Fixed Encodings and Enumerations¶

    Storing Fixed Encodings in an object¶

    RISC-V opcodes and ALU control codes are already fixed by the design, so it makes sense to keep them together in an object:

    object AluOp {
  val ADD = 0.U(4.W)
  val SUB = 1.U(4.W)
  val AND = 2.U(4.W)
  val OR  = 3.U(4.W)
  val XOR = 4.U(4.W)
}

    In use you write AluOp.ADD. Compared with 0.U and 1.U scattered all over the place, the name tells you what those bits mean.

    ChiselEnum¶

    A state machine has only a handful of states, so prefer the more strongly typed ChiselEnum:

    import chisel3.util.ChiselEnum

object State extends ChiselEnum {
  val IDLE, RUN, DONE = Value
}

val state = RegInit(State.IDLE)
when(state === State.IDLE) {
  state := State.RUN
}

    Enumeration values have a type of their own, so if you mistakenly connect a plain UInt straight to a state signal, the compiler is much more likely to catch it for you.

    Enum(n)¶

    Enum(n) is also common in older code and in shorter examples. It generates a number of plain UInt constants:

    import chisel3.util.Enum

val idle :: run :: done :: Nil = Enum(3)
val state = RegInit(idle)

when(state === idle) {
  state := run
}

    :: is Scala's list-decomposition syntax. The three values above correspond in order to 0.U, 1.U, and 2.U. It is fairly lightweight, but its type checking is not as strict as ChiselEnum's.

    Tip

    In the labs, prefer ChiselEnum for state machines; when reading existing projects, you need to recognize both forms.

    Type Conversions¶

    asSInt and asUInt¶

    These two operations do not change the underlying bits; they only change whether those bits are interpreted as signed or unsigned:

    val bits = "b1111".U(4.W)
val signed = bits.asSInt

    Read as a UInt, bits is 15; read as four-bit two's complement, signed is -1. The common uses in a CPU are SLT and SRA:

    val slt = a.asSInt < b.asSInt
val sra = (a.asSInt >> b(4, 0)).asUInt

    Forgetting the conversion usually does not produce a syntax error; it quietly generates a different but perfectly legal circuit. So signed comparisons, negative numbers, and inputs whose top bit is 1 must all be tested separately.

    Warning

    Take the signed and unsigned side of things seriously, or your results will simply come out wrong!

    asTypeOf¶

    asTypeOf reinterprets a group of bits according to the structure of the target type; it is very common when clearing a pipeline Bundle:

    val bubble = 0.U.asTypeOf(new ID2EX)
    It clears the whole structure of the target type in one step.

    Wire¶

    Wire represents a signal driven by combinational logic. It does not hold its value from the previous cycle.

    val result = Wire(UInt(32.W))
result := io.a + io.b

    When a combinational result has a default path and a special path, you can give the default connection first and then override it:

    val nextPC = WireDefault(pc + 4.U)

when(branchTaken) {
  nextPC := branchTarget
}

    This generates multiplexer logic. When the condition is false the path goes through pc + 4; when it is true it goes through branchTarget.

    Use DontCare with care

    DontCare says that certain bits do not matter, and synthesis may optimize them away. It also makes simulation harder to read, and can even hide illegal control paths. For CPU control signals, give explicit default values first.

    Explicit reset

    Whether it is the Wire introduced here or the Reg registers introduced later, prefer the versions that carry a default value, so that Vivado simulation does not show X (unknown) states!

    Reg and RegInit¶

    Reg and RegInit generate registers. The input is sampled on the clock edge, and the output holds between two clock edges.

    val pc = RegInit("h80000000".U(32.W))
pc := pc + 4.U

    RegInit specifies a reset value; Reg only specifies a type:

    val valid = RegInit(false.B)
val data = Reg(UInt(32.W))

    The contents of data, which has no reset value, should not be relied on after reset. The usual practice in a pipeline is to reset the valid bit of every stage and leave the data fields unreset; as long as valid is false, that data must not produce side effects such as writing a register or writing memory.

    The PC, state machines, pipeline valid bits, and any state that controls external side effects should normally have an explicit reset.

    Reset is mandatory for the control path and unnecessary for the data path — leaving the data path unreset avoids extra area and timing pressure.

    IO: Module Ports¶

    IO declares the ports that connect a module to the outside world. The usual style is to put the ports in a Bundle:

    class Alu extends Module {
  val io = IO(new Bundle {
    val a = Input(UInt(32.W))
    val b = Input(UInt(32.W))
    val out = Output(UInt(32.W))
  })

  io.out := io.a + io.b
}

    Seen from inside the module, an Input can only be read, while an Output is driven by the current module. Chisel checks port directions, so trying to connect an internal result to an input port is an error.

    io is the conventional name for the port variable, not something the language requires. Sticking to it makes it easier to read the interface of one module after another.

    Chapter Summary¶

    • Scala's if, for, and Int work during generation; Chisel's when, UInt, and Reg describe hardware.
    • What val fixes is the Scala name; the contents of a register can still change every cycle.
    • UInt(32.W) is a hardware type template; only once it is handed to Wire, Reg, or IO does it become a signal with an owner.
    • A Wire has no memory, so every combinational path must be fully driven; a Reg holds state across cycles.
    • = defines or rebinds a Scala name; := is what performs a hardware connection.

    The next chapter builds combinational and sequential logic on top of these signals, and focuses on when, default connections, connection priority, and arithmetic bit widths.
